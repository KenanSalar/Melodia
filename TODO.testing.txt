================================================================================

Eight cases across the two crates, no production change, and one piece of this entry's own
advice refused after reading the file it was about.

**The refusal: "take the floor up to an equality while there" was wrong and the entry should
not have said it.** `!ops_for(vt).is_empty()` is a floor, but the file already pins each
list's *length* against the Slint array it mirrors and each list's *first* element by name,
so the content is not unheld. Asserting the exact op lists on top of that buys nothing and
costs a failure on every legitimate operator addition, which is a change detector. The
shape table is an equality over the same set and is not one, because a new operator failing
it is a new operator that has not said what value it takes. `field_value_types_and_operator_lists_are_coherent`
is left exactly as it was.

**The sweep is a loop, deliberately, and the table is what keeps it honest.** Writing the
expected shape per row and asserting `from_input` against it is the table `.claude/rules/testing.md`
asks for; deriving the expectation from `input_kind` would have restated the code under
test and passed against every mutation below. The loop is over the table, not in place of it.

**Every pin was broken on purpose, one at a time, with the tree restored between.** Six
mutations, and the two-layer defence confirmed end to end: adding `RuleOp::Is` to `DATE_OPS`
fails the shape table with "a new operator owes OFFERED_SHAPES a row saying what value it
takes", and *then* declaring that row as `Shape::Text` (the fix the message asks for) fails
the sweep with "Date + Is is skipped by the evaluator, not rendered". Making a text operator
fall through to the always-false term fails the store sweep naming the pair; swapping the
widget codes fails only the widget test; dropping the text trim fails only the trim test.

**Two mutations fail more than one test and the entry says which.** Building `Days` as a
`Number` fails the sweep plus the trim and unparseable cases, both of which carry `Days`
assertions of their own. Breaking a text operator's arm fails the store sweep plus the
pre-existing `the_album_artist_rule_reads_its_own_column`, which uses `Is`. Honest rather
than ideal, and neither is the primary pin going quiet.

**`a_rule_whose_value_shape_is_wrong_renders_as_matching_nothing` is not a duplicate of
the pre-existing `an_incoherent_rule_is_dropped_rather_than_matching_nothing`**, which was
checked before it was written. That one proves the gate filters an incoherent rule out so
its siblings still apply; it can never see `push_false`, because the rule never reaches it.
The new one calls `push_rule` directly and pins that the fallback is `0` and not `1`. Change
`push_false` to push `"1"` and the old test still passes.

    melodia-core/src/entities/smart_criteria.rs         71.3% of 101    4 of 22 fns never run
    melodia-store/.../queries/smart_playlist.rs         84.9% of 225    1 of 19 fns never run

Three functions on one path are at zero, and they are the two ends and the symptom of a
single invariant that nothing states in code:

    RuleOp::input_kind         smart_criteria.rs:416   never executed
    RuleValue::from_input      smart_criteria.rs:433   never executed
    push_false                 smart_playlist.rs:142   never executed, 12 call sites

`from_input(value_type, op, raw)` is what turns what the user typed in the rule editor
into a `RuleValue`. `rule_is_renderable` is what decides whether that rule reaches SQL,
and it demands a specific value *shape* per operator: `Text` for the six text operators,
`Number` for the six numeric ones, `Days` for the two relative-date ones, `None` for the
four presence and boolean ones. Nothing checks that the two agree.

**The failure is silent and it is not "the rule is ignored".** `push_where` filters to
renderable rules first, and its own doc says the rest: "an all-skipped rule set yields no
`WHERE` (matches the whole library)". So a disagreement between the editor's value shape
and the evaluator's expectation does not produce an error, a log line, or an empty
playlist. It produces a smart playlist containing **every track in the library**.

The invariant holds today. Traced by hand across all four `ops_for` lists:

    ValueType   ops offered                          from_input gives   renderable wants
    ---------------------------------------------------------------------------------
    Text        Contains NotContains Is IsNot        Text               Text        ok
                StartsWith EndsWith
    Text        IsSet IsNotSet                       None               None        ok
    Number      Eq Ne Gt Gte Lt Lte                  Number             Number      ok
    Number      IsSet IsNotSet                       None               None        ok
    Bool        IsTrue IsFalse                       None               None        ok
    Date        InLast NotInLast                     Days               Days        ok
    Date        IsSet IsNotSet                       None               None        ok

So this is a pin, not a bug report, and the case is worth writing precisely because of
how the table above is held together: `input_kind`'s text branch is a catch-all
(`_ => match value_type { Text => Text, _ => Number }`). Add `RuleOp::Is` to `DATE_OPS`,
which is what "date is exactly" would be, and the editor offers it, `from_input` returns
`Number` because the field is not text, `rule_is_renderable` wants `Text`, the rule is
skipped, and if it was the only rule the playlist becomes the library. Nothing in the
tree fails.

The case is the sweep, not one row: for every `RuleField` (16) and every op in
`ops_for(field.value_type())`, a rule built through `from_input` from a representative
raw string must satisfy `rule_is_renderable`. That is 288 combinations screened down to
the offered ones, it is pure, and it needs no pool.

**On the loop.** `.claude/rules/testing.md` bans logic around an assertion and prescribes
a table with the expected value written out. The expected value here is uniform across
every row, so there is nothing per-row to write down and the honest shape is the
exhaustive sweep with the failing `(field, op)` pair in the message. That is the same
argument the corpus walks in `crates/melodia/tests/` already make. It stays beside the
file rather than moving there, because it is a question about two named modules and not
about the tree.

Two homes, because the invariant has two halves and neither crate can see both:

  1.1  `melodia-core`, in `entities/tests/smart_criteria_tests.rs`: every op `ops_for`
       offers for a value type produces the `RuleValue` shape that op's `input_kind`
       promises, and the four presence/boolean operators produce `None` rather than an
       empty `Text`. This is the half a future `DATE_OPS` edit breaks first.

       **That suite already has `field_value_types_and_operator_lists_are_coherent`, and
       reading it is what this entry turns on.** It spot-checks four of the sixteen
       fields' value types and then asserts `!ops_for(vt).is_empty()` for each of the
       four categories. Neither `from_input` nor `input_kind` is named anywhere in the
       file. So the coherence the name promises is not the coherence that matters here.

       [The `is_empty` half was called a floor worth raising, and that was wrong: the
       list's length is already pinned against the Slint array and its first element by
       name, so an equality on top would only fail on legitimate additions. Left as it
       was. See the SPENT note above.]

  1.2  `melodia-store`, in `queries/tests/smart_playlist_tests.rs`: the same sweep
       carried through to the evaluator, asserting the rendered predicate is not the
       always-false term. `push_false` going from 0 to non-zero executions is not the
       goal and should not be used as the check; the goal is that it stays at zero for
       every rule the editor can build. The one case that should *reach* it is a rule
       hand-built with a deliberately mismatched value shape, which is the internal

Check both by breaking the code: add `RuleOp::Is` to `DATE_OPS` and watch 1.1 fail, then
put it back and flip one arm of `rule_is_renderable` and watch 1.2 fail. If 1.2 passes
against the `DATE_OPS` edit, it is asserting the wrong thing.

PHASE 2: THE THREE MUTATIONS ONE PREDICATE IS SUPPOSED TO GATE   [SPENT]
================================================================================

Five cases and one extraction. `SweepProgress` holds the index and the `looked_up` tally,
and `advance_past` is the only thing that moves either, together with the attempted set.
The loop's three-effect `if` becomes one call.

**The entry's premise was confirmed rather than assumed.** All three mutations were applied
one at a time, and under every one of them
`only_a_rate_limit_keeps_the_chunk_it_was_refused_over` kept passing. The decision table's
own cases are blind to the loop misusing it, which is what the entry claimed and what makes
`retires_chunk` at 100% coverage worth nothing here:

  - attempted set written outside the guard: the two "moves nothing" cases fail. A 429's
    tracks join the permanent skip list having never been asked about.
  - index advanced outside the guard: those two plus
    `the_chunk_a_rate_limit_kept_is_the_one_retried_next`, with "the retry has to start
    where the refusal did".
  - `looked_up` counted outside the guard: those two, and the retry case catches the double
    count at `(3, 6)` against `(3, 3)`.

**The extraction removed a second spelling of one number.** `idx = end` and
`looked_up += chunk.len()` were the same quantity written two ways, `end` being
`min(idx + MAX_LOOKUPS_PER_POST, len)`. `advance_past` takes the chunk's ids and derives all
three effects from that one length, so the index and the count cannot disagree about how big
the chunk was. `end` survives only as the slice bound.

**`run_sweep` was left where the entry put it.** Its two decisions still take an `&AppState`
and are worth a case each only if something else builds that fixture.

    melodia-app/src/tasks/mbid_backfill.rs   24.5% of 184   11 of 19 fns never run

`BatchStep` is thoroughly tested. `retires_chunk`, `wait_before_next` and `for_outcome`
have four cases between them, including the one that matters most, named for its own
consequence: `only_a_rate_limit_keeps_the_chunk_it_was_refused_over`. The decision table
is not the gap.

`backfill` is, at 0% of lines 199 to 297, and what is uncovered is the *use* of that
table. The loop gates three separate mutations on one call:

    if step.retires_chunk() {
        for (id, ..) in chunk { attempted.insert(*id); }
        looked_up += chunk.len();
        idx = end;
    }

Each of the three has its own failure and no test can see any of them:

  - `attempted.insert` outside the guard: a 429'd chunk joins the persisted skip list.
    Those tracks are then unreachable by every later sweep and every later launch until
    the user finds the manual re-sweep button, which is the exact cost the `Throttled`
    variant's doc comment says it exists to avoid.
  - `idx = end` outside the guard: a 429'd chunk is stepped past within this sweep.
    Milder, since the ids stay out of `attempted` and the next sweep retries.
  - `looked_up` outside the guard: the count drives `run_sweep`'s persist decision
    (`if outcome.looked_up > 0`) and the user-facing toast, so a throttled sweep that
    resolved nothing reports that it looked tracks up and writes the set to disk.

`retires_chunk` being correct in isolation is what makes this invisible. Its own test
passes against every one of the three mutations above.

**Read this before pricing the seam, because round four ended on exactly this trap.** The
argument list is not the obstacle and never was: `backfill` takes `&AppState` for
`state.db`, `state.http_client()` and `mbid::write_resolved_mbids`, and the base URL is
`listenbrainz::LB_API_BASE` spelled at the call site rather than passed in. The question
to answer first is what a passing test would *assert*. Driving the whole loop means a
pool, a client, a server the lookup can be pointed at, and a token, and the assertion at
the end of all of it is still about three integers.

So the shape to argue for is the structural one, not the seam: the advance step is a pure
function of `(step, idx, end, chunk_ids)` returning the new index, the ids to retire and
the count to add, and the loop applies what it returns. That makes all three mutations
testable together with no pool, no server and no `AppState`, and it removes a three-thing
`if` from a loop body that is already doing five things. Write the extraction first,
argue it at the function, then the cases are a small table.

Do not extend this to `run_sweep`. Its two decisions (persist when `looked_up > 0`,
toast only when `announce`) are worth a case each once the above exists and it takes the
same `&AppState`; they are not worth a fixture on their own.

PHASE 3: THE ORDER TWO WELL-TESTED FILTERS ARE APPLIED IN   [SPENT]
================================================================================

The extraction was accepted, and five cases went in behind it. `BatchPlan` is the three
things a batch can turn out to be, `plan_batch` decides which, and the loop is a drain,
a plan and a match over it. `SelfWrites::default()` is the whole fixture; the `&AppState`
this entry was worried about never came into it.

**The boundary is after `deduplicate_events`, not around it, and that is the one design
decision here.** Wrapping dedup would have made the defensive `any` unreachable through
`plan_batch`, because dedup collapses a rescan batch to the singleton and nothing could
then hand the check a batch where the flag is not alone. The check's whole contract is
that it holds *independently* of dedup, so the function has to be reachable with a batch
dedup would never produce. `plan_batch` is therefore correct for any batch rather than
only a deduplicated one, which its doc says.

**This entry was wrong about the ordering it was written to defend, and the correction is
the interesting part.** It claimed that suppressing before the rescan check means "a
`RescanNeeded` arriving in the same batch as our own tag write can be filtered away". That
cannot happen: `suppress_self_writes` drops only `Modified`, so a `RescanNeeded` passes
through it by construction. Confirmed by mutation, not by reading alone: with the two
steps swapped, the plan is still `Rescan`.

The real cost is quieter and is stated in a different file. `take_recent` *consumes*, so
suppressing first spends the mark on a batch that is about to be thrown away for a full
reconcile, and the write's actual echo then arrives unsuppressed inside its TTL, costing
the re-hash, the lofty re-parse and the artwork re-extract that the set exists to avoid.
`melodia-core`'s `self_writes.rs` header lists exactly this under "Accepted trades" as
settled, describing behaviour that lives in this loop, and nothing held the two together.
That is the two-copies-of-one-argument shape `CLAUDE.md` warns about, and the pin now sits
on the side that can actually break.

Three mutations, each applied alone:

  - `any` replaced by the slice pattern `[FileEvent::RescanNeeded]`, which is the tempting
    simplification: both rescan cases fail, on "a rescan routed into process_batch is a
    panic, not a slow path". `dedup_rescan_supersedes_everything_in_batch` keeps passing,
    which is why nothing caught this before.
  - suppression moved ahead of the rescan check: exactly one case fails, on "the mark has
    to survive to suppress the echo when it actually arrives". The plan is still `Rescan`,
    which is the entry's error above made visible.
  - suppression skipped entirely: the mixed-batch case fails printing both events where one
    was expected, and the all-suppressed case fails.

    melodia-app/src/tasks/file_event_processor/mod.rs   13.5% of 52   4 of 6 fns never run

`deduplicate_events` has nine cases in `file_event_processor_tests.rs`, including
`dedup_rescan_supersedes_everything_in_batch`. `suppress_self_writes` has four, including
`suppress_can_empty_the_batch`. Both are correct in isolation and neither is the subject.

The subject is the loop in `spawn`, uncovered end to end, which applies them in an order
two comments argue for at length:

    dedup -> RescanNeeded short-circuit -> suppress_self_writes -> process_batch

The comments say why, and both halves are reversible without breaking a compile or a
test. [Putting suppression first was described here as letting a `RescanNeeded` be
"filtered away", quoting the comment that says so. That is wrong, and the SPENT note
above has the correction and what the real cost turned out to be.] Putting
`process_batch` before suppression means
every file we wrote a tag to is re-hashed, re-parsed and re-extracted, which is a
performance property with a correctness edge, since a re-ingest is the path
`CLAUDE.md` says drops ratings, play counts and favourites when the move-detection halves
lose to each other.

This is the composition gap, and it is the one shape round four's thesis retirement did
not cover: two primitives fully pinned, their sequencing pinned nowhere.

**Price the fixture before promising the case.** The loop reads `state.self_writes`,
`state.rescan_notice`, `state.library_changed` and calls `reconcile_watched_folders`, so
driving it whole needs a booted `AppState`, which four documents have now declined to
build. The cheaper answer is the same one phase 2 wants: the ordering is a pure
classification of a batch. Given a batch and the `SelfWrites` set, decide between
"reconcile everything", "process this reduced batch" and "nothing to do". That function
takes `(Vec<FileEvent>, &SelfWrites)`, returns an enum, has no `AppState` in it, and the
loop becomes a match over its answer. The three arms are then a table.

If that extraction is rejected, this entry is declined rather than done halfway. A test
that drives the loop through a real `AppState` to assert an ordering is the end-to-end
answer to a question a unit test can hold, which `.claude/rules/testing.md` names
directly.

     Wrapping one more call would have put the defensive check out of reach of every test
     that could ever fail on it.

With phases 1 through 3 spent, what remains on this list is phase 4's two small entries.
The next round starts from a fresh measurement, not from this document's rows.

Three things to carry into every entry, all of them findings the last three documents
ended on rather than predictions:

  **The mutation is what reviews the test.** Round three shipped a pin that passed against
  the code it was written to catch, and round four shipped one that passed because a
  process-wide `OnceLock` filter swallowed the arm it was testing. Break the function on
  purpose, watch that test and only that test fail, and do it even when the test looks
  obviously right.

  **A seam and an observation are different questions.** Round four's phase 1 refused two
  of six cases after checking only the argument list. Ask what a passing test would
  *assert* before writing "the seam is already there", and price the arming as carefully
  as the parameters. Phase 2 here is the same trap and is written to be read that way.

  **Read the file before writing against it.** Five of round two's seven entries were
  wrong about where their own value sat, and round four's phase 5 was written against a
  file whose decision table was already the best-covered thing in it. In this document
  `folders.rs` was the candidate that did not survive the read, and `smart_criteria.rs`,
  at 71% and never a suspect, is phase 1.
