1.1  `a_nonzero_exit_fails_the_smoke_test`, which fails on a kernel race
-----------------------------------------------------------------------

Observed, once, on the second of three instrumented runs made for this document:

    panicked at crates/melodia-app/src/services/updater/tests/verify_tests.rs:57:5:
    the exit code is what a bug report needs: post-swap launch verification:
    failed to spawn /tmp/.tmp9ldQxE/Melodia --version: Text file busy (os error 26)

Eight subsequent uninstrumented runs of the full `melodia-app --lib` suite passed, so
the window is small and instrumentation widens it. That is the profile of a flake,
not evidence against one.

ETXTBSY on `execve` means some process holds the file open for writing. The only
writer is `fake_binary`, which is `std::fs::write` plus a chmod, and its descriptor
is closed before the function returns. What keeps it open past that is another
thread: `verify_tests.rs` has four tests that each write a script into their own
tempdir and then spawn it, and they are the only tests in the crate that spawn
anything at all. Between one test's `fork` and its `exec`, the child holds every open
descriptor the parent had, including the one another test is part way through writing
its own double with. Rust opens with `O_CLOEXEC`, so the child drops it at its own
`exec`; the race is the gap before that.

The fix is the shape `.claude/rules/testing.md` already prescribes for environment
variables, for the same reason: serialize the mutation behind one lock per test
binary. The lock has to span write *and* exec, not just the write, since the window
is the pair. A `tokio::sync::Mutex::const_new(())` held across the `.await` is the
spelling that stays clippy-clean.

Not a retry. A blind retry on ETXTBSY is exactly the "paper over" the rule names, and
it would leave the same race live in any future test that writes an executable.

Check it by reasoning, not by running: the mutation is that no other test in the
binary forks while the lock is held, and there is no assertion that can observe a
race that fires once in fifty. What the entry owes instead is the argument written
down at the fixture, so the next person to add a fifth spawning test knows why the
lock is there.

1.2  `tasks/scrobble.rs`, the detector half
-------------------------------------------

    melodia-app/src/tasks/scrobble.rs   18.3% of 126 lines   10 of 13 fns never run

`spawn`, `run_detector`, `process_effects`, `fetch_row` and `now_ts` are never
executed. The submitter half of the same file has four cases and its own module doc,
which is where the decline to write these lives:

    "`run_detector` is not driven from here, its decisions being the pure
     `DetectorState`'s and covered by that module's suite."

That is right about the detector and wrong about the loop, and the three decisions it
walks past are not `DetectorState`'s:

  **The single-slot row cache.** `fetch_row` keys a cached `ScrobbleRow` on
  `track_id` and returns it when the id matches. The comment calls it "so a play's
  now-playing fetch is reused at its scrobble". Drop the `*id == track_id` guard and
  every scrobble after the first carries the *first* track's artist and title, for the
  rest of the session, to both providers. It is silent, it is permanent once
  submitted, and the user's own listening history is the only place it shows up. This
  is the case to write first and the one to break on purpose.

  **The priming.** `run_detector` is do-while shaped on purpose: each receiver's
  `borrow_and_update()` value is processed before the first `changed()`. Rewritten as
  a plain `loop { select! }` it compiles, passes anything the detector's own suite
  asks, and loses the track that was already playing when the task started, which is
  every track after a settings change that respawns the loop.

  **The shutdown.** The `select!` is `biased` with `shutdown.cancelled()` first, and
  the cancelled arm runs `detector.on_shutdown()`'s effects through `process_effects`
  *before* returning. Without it a listen in progress at quit is dropped rather than
  finalized, which is the one moment the user cannot retry.

Beside them, `process_effects`' own mapping: `Effect::Scrobble` and `Effect::Finalize`
share an arm, and a row that `ScrobbleTrack::from_row` refuses produces nothing.

Reach, all of it already built:

  - `DbPool::test_pool()` and `queries::fixtures::insert_test_track`, both already
    used by `tasks/tests/rating_import_tests.rs`. Note that fixture hard-codes
    `folder_id: 1`, so seed a folder row first or the failure is a bare
    `FOREIGN KEY constraint failed`.
  - `disconnected_service(dir)` already exists in `tasks/tests/scrobble_tests.rs`.
  - `watch::channel(None)` for both receivers, `CancellationToken` for the shutdown.
  - `PlayerViewModelLight` and `PositionTick` are public `melodia-engine` types.
    `melodia-integrations`' `vm()`/`tick()`/`summary()` helpers are `#[cfg(test)]`
    and do not cross the crate boundary, so a local copy here is correct rather than
    duplication to avoid.

**The one trap, and it decides how the cases are split.** `enqueue_scrobble` pushes
to the queue and wakes nobody; it opens no socket, so a service with ListenBrainz
armed makes `queued_len()` the observation for a Scrobble effect. `update_now_playing`
does the opposite: with a provider armed it `tokio::spawn`s a real POST at
`listenbrainz_base`, and `with_listenbrainz_base` is `pub(crate)` to
`melodia-integrations`, so nothing in `melodia-app` can point it anywhere. Every
now-playing case here runs against a **disconnected** service and observes the cache,
never the request. The submit path is phase 2's, in the crate that can redirect it.

Arm ListenBrainz, never Last.fm: `lastfm_scrobble_ready()` reads `option_env!` keys
baked in at compile time, so a keyed build and a keyless CI one disagree about whether
the test ran while reporting identically. `helpers.rs` in the scrobble suite says the
same thing one crate over; that argument is settled and applies here unchanged.

Six cases:

  - a cache hit returns the cached row and does not re-query
  - a different id re-queries and *replaces* the cache (the mutation above)
  - an id with no row answers `None` and leaves the cache holding what it held
  - a `Scrobble` effect against an armed provider queues one item, and `Finalize`
    queues the same one (the shared arm)
  - the primed view-model is processed before any `changed()` fires
  - a cancellation finalizes through `process_effects` before the loop returns

`now_ts` and `spawn` stay uncovered and should. One reads the wall clock, which the
rule says to pass in rather than test; the other is four `clone`s and two
`spawn_cancellable` calls, and its arguments are an `AppState`.

PHASE 2: THE PROVIDER WHOSE SEAM IS ON THE OTHER SIDE OF THE WALL
================================================================================

    scrobble/providers/listenbrainz.rs   57.7% of 241   15 of 41 fns never run
    scrobble/mod.rs                      69.9% of 266   12 of 49 fns never run

`validate_token`, `submit_playing_now`, `lookup_recording_mbids_bulk` and
`server_error` are never executed, and every one of them already takes a base URL.
`submit_tests.rs` drives the same service against `melodia_testkit::http::TestServer`
through `with_listenbrainz_base` three times over, so the server, the builder and the
shape are all written and these four simply have nothing calling them.

What each decides:

  **`validate_token`** is the gate the Settings page puts in front of a token the user
  pasted. A version that accepts on any 2xx accepts a token the server has told it is
  invalid, and the user finds out weeks later from an empty profile.

  **`server_error`** is the shared reading of a failed response body. It decides
  whether a failure is reported as the provider's own message or as a status code,
  which is the difference between a bug report that names the cause and one that does
  not.

  **`submit_playing_now`** is ephemeral by design, never queued and never retried, so
  nothing downstream can compensate for it being wrong.

Beside them in `mod.rs`, `mbid_lookup_token` is three lines and a two-condition
decision (auto-tag on **and** ListenBrainz connected), and it is now reachable without
a network because `set_listenbrainz_credentials` only writes the shadow and the file.
`update_now_playing` and `enqueue_scrobble` belong here rather than phase 1 for the
redirect, and `enqueue_scrobble`'s "a flag for a disconnected provider would never
clear and would pin the item through `retain_pending`" is a claim its own comment
makes and nothing holds.

Argue the split before writing: `update_now_playing` spawns and returns, so the
observation is the request arriving at the `TestServer`, and a test that awaits it
needs the spawn to have somewhere to run.

3.1  `tags::apply_tag_edit`'s no-op guard
-----------------------------------------

    melodia-app/src/library/tags.rs   75.3% of 231   10 of 25 fns never run

`write_tag_edit` underneath is already "the testable core" and is covered. What is not
is the orchestrator, and its first line is the one that matters:

    // lofty rewrites the tag whether or not anything differs, so a reflexive
    // open-then-Save must not touch disk.
    if ids.is_empty() || edit.is_noop() { return Ok(TagEditReport::default()); }

Opening the Edit Track Information dialog on a selection and pressing Save without
changing anything must not rewrite every selected file. Losing that guard rewrites
tags across a whole selection, moves every mtime, and hands the watcher a batch of
changes the user did not make. The comment is a claim about a third-party library's
behaviour, which is the kind that goes stale silently.

Its two follow-on gates are the same shape and cheaper: the refetch and resync happen
only when the player actually references an edited track, and `library_changed` bumps
only when something landed.

Reach is `&AppState`, and the narrowing is round two's for the ninth time: the pieces
are `db`, `paths.artwork_dir`, `cover_cache`, `self_writes`, `player_state`, `sinks`
and `library_changed`, which is what `write_tag_edit` already takes most of. Price the
narrowing against the guard before taking it; the guard returns before touching any of
them, so the first case may not need one at all.

Three things to carry into every entry, all of them findings the last two documents
ended on rather than predictions:

  **The mutation is what reviews the test.** Round three shipped a pin that passed
  against the code it was written to catch, and review did not see it. Break the
  function on purpose, watch that test and only that test fail, and do it even when
  the test looks obviously right; that is the one it happened to.

  **Read the file before writing against it.** Five of round two's seven entries were
  wrong about where their own value was, always in the same direction: the percentage
  pointed at lines nothing ran, and the defect sat in lines that ran with nothing
  asserted over them. This document has already made that error once, in draft, about
  `submit.rs`.

  **"Needs an `AppState`" is an assumption until someone checks it.** Two backlogs
  deferred items onto a fixture nobody had priced, and when round three finally priced
  it, four of five items turned out to want a pool, a predicate, a free function and a
  needle on a walk that already existed. Price the fixture against the item after
  reading it, not before.
