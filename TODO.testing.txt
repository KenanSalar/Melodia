**`MIN_STATUS_SITES` is 1 and not 2, which is what the tree holds.** A floor equal to its
subject is an equality wearing a floor's clothes, and both `status` comparisons are the two
halves of one ternary: a legitimate rewrite of that expression would fail a floor of 2 while
the contract it guards is untouched. The other two floors sit well under their subjects for
the same reason. What a floor is for here is a walk whose needle drifted, which every
assertion standing on it would otherwise pass, and 1 catches that as well as 2 does.

**The two enums are checked one direction and the `variant` set both.** Round five would ask
for an equality; on the enums it would be wrong. `RepeatMode::All` is deliberately never
named in a comparison, the sheet distinguishing only "one" from "not off", so an equality
would fail on code that is correct. Containment still catches a rename from either side,
because renaming the Rust variant is exactly what makes the sheet's literal unproducible.
The `variant` half has no such asymmetry and is an equality.

**The finding worth keeping is that a mutation's *output* is worth reading even when the
mutation behaves.** Breaking the card's `"error"` arm failed the equality as intended, and
the failure message printed every producer it had found. Reading that list showed two of
them missing: `arg_literal` took the argument index as a comma count, so `commas == 0` could
never match anything, and the two `NotificationParams::plain("success", …)` sites in
`settings/diagnostics.rs` and `radio/callbacks/files.rs` were invisible to the walk. The
equality passed anyway, because "success" is produced at four other sites. A walk that
silently sees 29 of 31 producers is the shape this whole document exists to find, and
nothing but the printed list would have shown it. The fix is a `literal_at` that reads the
first argument straight after the `(`.

`melodia-store` is the best-covered subsystem in the tree and four of its reads have never

**2.1  `TrackMeta` is the one projection no test selects**

`entities/track.rs` carries five hand-maintained `SELECT` column lists, each paired with a
`#[derive(FromRow)]` struct and each a runtime failure if the two disagree: sqlx matches by
column name and errors at fetch time, so adding a field to the struct and forgetting the
const compiles clean and fails on the user's machine.

Four of the five are executed by some test. `TRACK_META_COLUMNS` / `track_meta_columns()` is
not, and neither is its only reader, `queries::track::get_track_meta`. That is the chip row
on the full-screen Now Playing view.

The fixture exists. `queries/tests/track_tests.rs` has 51 cases and `seed_db()` at the top of
it; this is one more `#[tokio::test]` against `DbPool::test_pool()`. Assert the projected
fields against the seeded row rather than merely that the call returns `Ok`: a `SELECT` that
runs proves the schema, and only the field comparison proves the struct.

Take the `None` arm too. `get_track_meta` is documented to answer `None` for a missing id
because the caller renders empty chips, which is the difference between an empty chip row
and an error toast.

**2.2  Three neighbours, one case each**

  `get_track_file_path`  the "Open Containing Folder" projection, and the leanest one
  `count_tracks`         what the diagnostics bundle reports as library shape
  `get_favorite_artists` (`queries/artist.rs:48`) never executed either

None needs a seam. All three are `DbPool` in, value out, against a fixture two files already
build. Write the empty-library and missing-id partitions, not only the happy path:
`count_tracks` on a fresh pool is the answer a diagnostics reader trusts.

**2.3  The one path SQLite parses as SQL**

`database/backup.rs::create` interpolates the staging path into `VACUUM INTO '…'` because
that statement takes no bind parameter, and doubles any `'` in it so a directory name with
an apostrophe cannot end the literal early. Nothing tests that. Every backup test builds its
directory with `tempfile::tempdir()`, which never produces one.

This is a boundary case with a fatal blast radius: `main.rs` treats a failed backup as fatal
to startup, so a user whose data directory sits under a folder with an apostrophe in it
would be unable to launch at all after a migration lands. `MELODIA_DATA_DIR` makes that
directory the user's choice, and on Windows and macOS an apostrophe in a home folder name is
ordinary.

One case: a backups directory named with an apostrophe, and the backup opens as a database
afterwards. `a_backup_round_trips_as_an_openable_database` is the shape to copy.

**Cost of the phase:** no production change. Five or six cases in two existing suites.

PHASE 4: THE TWO CADENCES INSIDE THE LOOP NOTHING RUNS
================================================================================

Last, and the only entry needing a production change. Price it before starting.

`spawn_playback_monitor` (`engine/handlers.rs:260`) is a 198-line body at zero. Its decision
helpers are covered: `evaluate_playing_tick` and its `PlayingTick` have cases in
`handlers_tests.rs`. What has none is what the loop does *with* them, and two of those are
numbers written inline:

    media_tick_counter = (media_tick_counter + 1) % 10;   // "~5 seconds"
    save_tick_counter  = (save_tick_counter  + 1) % 60;   // "~30s"

Both are derived from `POLL_INTERVAL_MS`, which is a named constant with a doc comment
arguing its value, and neither derivation is spelled anywhere. `.claude/rules/code-style.md`
and CLAUDE.md's no-magic-values rule both point at the same edit independently of coverage.

Two properties are worth a test and they are not the same size.

  **The save cadence bounds a data-loss window.** The queue and position snapshot survives
  SIGKILL; the clean-exit snapshot is elsewhere. Sixty becoming six is write amplification
  on every playing tick, and sixty becoming six hundred is five minutes of queue the user
  loses to a crash. Neither is visible.

  **The publish gate is a stated performance property.** `last_published_second` is seeded
  `u64::MAX` specifically so the first tick after playback starts always publishes, and the
  comment above it argues the 2 Hz to 1 Hz halving in terms of renderer cache churn and
  property-binding dirty marks. The seed is the interesting half: losing it means the
  now-playing bar shows nothing until the first whole-second boundary.

**The seam does not exist and this entry is not pretending otherwise.** Round five declined
`material_you::run` for the same shape after pricing the payoff at one boolean. The
difference claimed here is that these are two properties with named costs rather than one,
and that the same edit is owed under a rule that has nothing to do with testing. That
argument is the entry's premise, not its conclusion. **Read the loop and price the
extraction before writing any of it**, and if the honest answer is that a helper holding
"what does this tick owe" is smaller than the cases it buys, say so in the commit and stop.

Scope it tightly if it goes ahead: two named constants asserted against `POLL_INTERVAL_MS`,
and a pure helper over the two counters plus `last_published_second`. Nothing in the phase
needs `emit_and_execute`, a backend or a device.

**Mutations to run:** seed `last_published_second` at `0` and watch the first-tick case
fail. Move the save counter above the `!is_playing` short circuit and watch the
playing-ticks-only case fail.

Three things to carry into every entry, all of them findings the last four documents ended
on rather than predictions.

  **The mutation is what reviews the test.** Round three shipped a pin that passed against
  the code it was written to catch, and round four shipped one that passed because a
  process-wide `OnceLock` filter swallowed the arm under test. Break the function on
  purpose, watch that test and only that test fail, and do it even when the test looks
  obviously right.

  **An entry can be wrong about the test it is asking for, not only about where the value
  is.** Round five's phase 1 asked for a floor to be raised to an equality and the file
  showed the content was already held two other ways. Phase 4 here is written to be refused
  if the read says so.

  **Check the neighbours before adding a case that sounds like one of them.** Phases 1, 2
  and 3 are all the same discovery: a function whose siblings are tested, whose own name
  makes it look covered, and which is the one production actually calls.
