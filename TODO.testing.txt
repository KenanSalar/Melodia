P0.1  three tests in `queue_tests.rs` named after doors they never call  [SPENT]
-----------------------------------------------------------------------

Not a gap. A pin that cannot fail, which `.claude/rules/testing.md` calls worse
than no pin, and it is first because it is the one thing here that is actively
misleading rather than merely absent. The instrumented run is what surfaced it:
`queue_set_shuffle`, `queue_toggle_shuffle` and `queue_cycle_repeat` are all three
never executed, while three tests bearing their names pass.

  `queue_set_shuffle_noop_when_already_enabled` calls `shuffle_inline` and then
  asserts `state.queue.shuffle_enabled` twice, the second time through a local
  bound from the first. The idempotent no-op it names is a branch inside
  `queue_set_shuffle` that the test never reaches, and the door could be deleted
  outright with the suite green.

  `queue_toggle_shuffle_enables_then_disables` reimplements the door's body inline,
  twice, as an `if/else` over `shuffle_enabled`. It holds that the copy in the test
  file behaves as expected. It also carries conditionals around its assertions,
  which the rule names outright.

  `queue_cycle_repeat_cycles_correctly` calls `state.queue.cycle_repeat_mode()`,
  which is `melodia-engine`'s method and is already pinned by that crate's own
  `queue_tests.rs` and `state_tests.rs`. Same mistake round two's step 6 recorded
  and corrected in the net tier: a case pinning a sibling suite's claim a second
  time.

What the doors actually decide, and what the replacements are for:

  the idempotent form. `queue_set_shuffle` returns the *resulting* state rather
  than the request, so a Shuffle pill pressed twice asks for `true` twice and
  reorders once. Its own comment says so. The case is two calls with the same
  argument and one reordering, and deleting the early return has to fail it.

  the persist kick. All three doors call `persist_shuffle` or `persist_repeat` with
  the value the state came back with, not the one that went in. A version writing
  the request persists a shuffle that never happened, and the next launch restores
  a reordered queue that is not reordered.

  the toggle over an empty queue, which is the partition neither door's test has:
  `shuffle_inline` on no tracks against `unshuffle` on no tracks.

Reach: all three take `&AppState` for `player_state`, `sinks` and `runtime`. The
narrowing is round two's, seven times over, and the seam under it already exists:
`with_state_emit(&state.player_state, &state.sinks, …)` is what the body does, and
`state::fixtures::test_sinks()` hands out the publish half. Take the persist kick
as a separate function over `&Paths` so the door keeps its signature.

Check the rewrite by breaking each door on purpose. All three current tests survive
deleting the function they name, which is how they got here.

Five cases in place of the three, and three private workers under doors whose
signatures did not move: `set_shuffle`, `toggle_shuffle` and `cycle_repeat`, each
over `(&PlayerStateHandle, &PlayerSinks)`. No call site moved and `melodia-views`
learned nothing.

**Two of this entry's own claims were wrong, in the same direction as every entry
in the last two documents.**

  The persist kick was not worth narrowing. `persist_{shuffle,repeat}` is a
  fire-and-forget `spawn_blocking` a test cannot await, and the property the entry
  was reaching for is not in it: what could be persisted wrongly is the *value*,
  and that value is the worker's return. Asserting the return is the same claim one
  layer down with no runtime, no temp root and no timing. `&Paths` would have bought
  a test of `mutate_settings`, which has its own suite.

  "The toggle over an empty queue" is not a partition either door distinguishes.
  What does is `set_shuffle`'s *answer*: `shuffle_play_order_in_place` returns
  before setting the flag when `play_order` is empty, so the request is `true` and
  the outcome is `false`, and that is the one input where returning `enabled`
  differs from returning the state. It is now the case the entry meant to be
  asking for.

**One of the five was a pin that could not fail, caught by the mutation and not by
review.** `turning_shuffle_off_puts_the_queue_back_in_the_order_it_was_added` first
asked for a shuffle and then asked for it off, and with `set_shuffle`'s two arms
swapped it passed: the `true` call unshuffles an already-ordered queue, the `false`
call takes the equality early return, and the order is untouched at both ends. It
arranges the shuffled order by hand now, which also takes the RNG out of the
assertion. The old shape would have missed a flag-clear-without-`unshuffle` once in
every hundred and twenty runs.

Every pin was checked by breaking the code: the equality guard, the returned state,
both arm swaps and the pre-cycle read. Each failed its own test. The arm swap fails
two, which is honest rather than ideal, and the entry says which.


P0.2  `rating_import::import`, the page loop nothing walks           [SPENT]
------------------------------------------------------------

`import` and `spawn` are never executed. `read_each` has its two cases and
`rating_tags` underneath it is at 100%, so what is missing is exactly the loop
between them.

This is the only pass that reads the stars sitting in a user's files into their
rows, it runs once per install, and it is `one_shot::OnFailure::Retry` precisely
because a marker recorded wrongly puts every one of those stars out of reach for
the life of the install. Its own doc comment argues that. Nothing holds it.

Four cases:

  the keyset advance. `after_id` takes the last row's id, and `set_rating` removes
  those rows from the predicate the next page asks with, so `id > after_id` is what
  stops a rewritten window skipping rows. An `OFFSET` rewrite passes a one-page
  test and skips half a library on the second page. Reaching a second page means
  `PAGE_ROWS` arriving as a parameter with the door spelling the constant, which is
  the seam-as-a-parameter shape the rule endorses rather than production API with
  only a test for a caller.

  the two ways a page ends. An empty page breaks; a page whose files carry no
  rating `continue`s. Those are different arms and only one of them advances, so a
  library where the first page happens to be unrated must not stop the pass.

  the group-by-rating write. Five values at most, one UPDATE each. A map keyed
  wrongly stamps one file's stars onto another's rows, and the loss is silent
  because a star is exactly the thing the user cannot check against a reference.

  `library_changed` bumps once, at the end, and only when something landed. Per
  page it costs the mounted section a re-query per page; on zero it repaints for
  nothing. `Signal` is observable from a test, so this is an assertion rather than
  a source-text pin.

Narrowing: `import(&AppState)` reaches `state.db` and `state.library_changed`.
`import_into(db, page_rows) -> AppResult<usize>` with the door bumping on a
non-zero count is B2's narrowing for the eighth time, and no call site moves.

Five cases, and the entry was right about all four of its claims, which is the
first time that has happened in three documents. The narrowing went exactly as
written: `import(&DbPool, &Signal)` over `import_into(&DbPool, i64)`, the one-shot
closure spelling `&state.db` and `&state.library_changed`, and nothing else moved.

Two things worth knowing before writing the next fixture over a pool:

  **`insert_test_track` hard-codes `folder_id: 1`**, so a suite that seeds tracks
  without a folder row fails on a bare `FOREIGN KEY constraint failed` naming
  neither. `queries::folder::insert_folder` first, as `setup_seeded_db` does.

  **The mutation for a keyset walk is the off-by-one, not the rewrite.**
  `after_id = last_id + 1` skips every other row at a page size of one and is a
  single character; standing up an `OFFSET` version to break turned out to be a
  worse test of the same thing, and the first attempt at it terminated correctly
  and proved nothing.

`Signal` is observable from a test through `subscribe()` plus `has_changed()`,
which is what made the two bump cases assertions rather than source-text pins.


P0.3  `mbid_backfill`'s four error arms, which decide what is never looked
      up again                                                       [SPENT]
------------------------------------------------------------------------------------

`backfill`, `run_sweep` and `spawn` are never executed. Six cases exist and all six
are on `load_attempted` / `persist_attempted` / `summarize`, which is the file
around the loop rather than the loop.

First among the reachable ones because defects have already clustered here:
CLAUDE.md names this file as the one where a rule and its doc comment came to
disagree about whether the attempted set was persisted, each correct on the day it
was written. The set is still the thing the file is about.

The decision is a four-row table over two outputs, whether the chunk joins
`attempted` and whether `idx` advances:

    Ok                -> mark, advance
    RateLimited       -> neither; back off and retry the same chunk
    InvalidToken      -> neither; break
    any other Err     -> mark, advance

The fourth row is the case worth writing. A 500 from ListenBrainz permanently skips
those tracks until the user finds the manual button, and it sits one `matches!`
away from the row that deliberately does not. The comment on it says "skip this
batch rather than spin on it", which is a decision and not an accident, so the test
is what stops someone tidying the two arms into one.

Beside it: cancellation mid-request. `run_until_cancelled` answering `None` breaks
*without* marking, which is the difference between a shutdown costing nothing and a
shutdown costing a chunk that never gets looked at again.

Take the cheap split first. The `match result` block is a pure decision over the
outcome and the chunk, with no I/O in it. Lift it to a free function answering what
to do and the four rows are a table with no server at all. Only then argue the
wider narrowing, which buys the HTTP path: `lookup_recording_mbids_bulk(client,
base_url, token, queries)` already takes the base URL, `melodia_testkit::http::
TestServer` is what the net suites drive, and `mbid::write_mbids(db, artwork_dir,
cover_cache, self_writes, resolved)` is the narrowed twin of the writer the loop
calls. Everything the wider version needs exists; the table is where the defect is.

Four cases over a `BatchStep` enum, and the wider narrowing was **not** taken and
should not be until something needs it: every row of the table is answerable with
no server, no pool and no runtime.

**The split paid for itself in the production code before any test ran, which is
not what the entry expected.** The mark-and-advance triple (`attempted.insert`,
`looked_up +=`, `idx = end`) was written out in two of the four arms and had to
stay in step between them; it is written once now, behind `retires_chunk()`. The
loop reads as classify, write what came back, retire or not, wait or stop.

**The entry's "cancellation mid-request" case was not taken.** It is real, and it
is already structural rather than conditional: `run_until_cancelled` answering
`None` breaks out of the loop above the classifier, so there is no arm that could
mark and no branch to get wrong. A test there would pin `tokio_util`.

Two things the shape decided that the entry did not name, both now pinned:

  the pacing asymmetry. `BATCH_PAUSE`'s own doc says "between successful batches",
  so a skipped batch moves straight on and an answered one waits. Folding them
  would have been invisible and is now a case.

  the throttle's wait comes from `rate_limit_backoff(reset_in_secs)`, so the
  server's own `Retry-After` reaches the sleep. A constant there either hammers a
  server asking for a minute or parks for one over a server asking for a second.

`Skipped` waits `Duration::ZERO` rather than not sleeping at all, which is the one
behaviour that moved: a yield and a cancellation point where there was neither.


P0.4  `open_files`, the file-association entry point                 [SPENT]
------------------------------------------------------

`open_files` and `queue_import_files` are two of the fifteen functions in this file
never executed. The other thirteen are P0.1's three plus round two's declined
transport wrappers, and those stay declined.

This is the Rust end of the handoff CLAUDE.md spends a whole paragraph on: `%F` on
four `.desktop` sources plus the `sed` that must not eat it, `wix/main.wxs`'s
`FileAssociations`, the single-instance claim, `serve_file_opens`' backlog. Every
one of those halves is pinned somewhere. The function they all hand to is not.

Three documented claims, none held:

  ids come off the sorted summaries rather than `ImportFilesResult::track_ids`,
  which arrive partly out of a `HashMap`. The doc comment says this in as many
  words. Swap them and the track that plays is whichever the hash order put first:
  stable within a build, different across builds, and impossible to read as a bug
  from the outside. This is the one to write first and the one to break on purpose.

  a set where nothing could be read is an `AppError::Queue`, not a silent empty
  queue. Double-clicking a corrupt file has to say something.

  the sibling difference. `open_files` replaces the queue, `queue_import_files`
  appends to it, and the doc comment says they differ in nothing else. Collapsing
  them is a one-word edit and costs the user the queue they were listening to.

Reach: `import_files_with_summaries(state, …)` is already a two-line door over
`import_and_summarize(db, artwork_dir, cover_cache, paths)`, and `player_play_
tracks` takes a `PlaybackContext`, which `state::fixtures::TestPlayback` hands out
with real files under it through `stage_playable`. So this is a narrowing onto
pieces that already exist, not a new seam.

Four cases over `open_as_queue` and `append_imported`, both
`(&PlaybackContext, &CoverCache, &[String])`. **`import_files_with_summaries` is
gone rather than narrowed**: it existed to spell three fields out of an
`&AppState` for two call sites, `playlists.rs` was already spelling them itself,
and with both queue workers taking a context there was no caller left. That is the
last `&AppState` reach out of `library/import.rs`.

**One of the four cases claimed something false and the mutation is what said so.**
Its `///` had `Some(0)` as the start slot buying something over `None`, and
`resolve_start_slot` falls back to the head either way, so the two calls are
identical. The case is still live and still distinct from the one above it, for a
different reason the comment now gives: the sibling pins the list, this pins which
of it plays, and a queue in the right order with `current_index` elsewhere is the
same bug from the listener's side.

The ordering pins are deterministic because titles are written into the fixtures
through `tag_writer::apply_to_file` and `natord` disagrees with a plain string
compare on "Track 2" against "Track 10", so input order, lexicographic order and
the right answer are three different sequences. `get_track_summaries_by_ids`
re-orders its rows to the ids it was handed, which is what carries the sort
through `player_play_tracks` to the screen; without that the sort would be
discarded one call later and none of this would be observable.

So the work here is not another narrowing. It is a fixture, and the argument to
have before writing one is what a boot costs: `AppState::init` opens the card,
which under CI is `.github/actions/headless-audio` pointing ALSA's default PCM at
the userspace null device, plus a migration run and a backup per boot. That is the
whole reason this is one entry rather than five. Build it once in
`crates/melodia/tests/common/`, alongside the mixer helpers already there, and put
every declined item through it. Whether one booted state is shared across cases or
each case boots its own is the first thing to settle, and the rule's answer is
independence unless the measurement says otherwise.

What it unlocks, in the order their cost falls:

  one_shot.rs. Both `OnFailure` arms, which is the only knob in the file: whether a
  pass that failed part way still records its marker. `rating_import` is the
  `Retry` consumer and `artwork_renormalize` the `Mark` one, so the arms are
  drivable through the real sweeps rather than a synthetic one. Plus `Sweep`'s
  `label`/`marker` split, whose failure mode is a bug report reading "ratings_
  imported_from_tags failed" instead of "Rating import failed", invisible until
  someone reads one.

  library/settings/folders.rs. `reconcile_watched_folders`' CAS gate,
  `toggle_folder_watching`, `set_folder_watching_enabled`. Round two called a
  source-text assertion on the CAS gate "weaker than no assertion reading as
  coverage" and left them. At this level they are drivable for real, and the
  cascade underneath `add_folder` already has its three cases from step 4.

  the Radio off switch as a table. With the flag off every door answers
  `AppError::Settings`. `radio_facade.rs` walks every file under `library/radio`
  for the `.http_client()` reach and structurally cannot see a door added past
  `ensure_enabled`; the walk and the table together can. This is the claim round
  two wanted and could not write.

  first_launch.rs. Auto-adds `dirs::audio_dir()` once and its duplicate check
  canonicalizes both sides. It reads `dirs::audio_dir()` directly, so the honest
  case is the *second* launch: with `music_folder_auto_added` already set it must
  touch neither the folder table nor the watcher. The first-launch arm needs the
  home directory pointed somewhere, which is the env lock, so take the second-
  launch half and say why the first is not there.

  radio_logo_cache.rs. Prune then sweep, in that order, because reversed the sweep
  sees every dropped row's file still referenced and the store never shrinks. Its
  `//!` argues the ordering and nothing holds it. This one is also narrowable to
  `(&DbPool, &Paths)` like `artwork_sweep::run` beside it, which would move it to
  P2 and cost no boot at all. Argue which before writing it; the narrowing is
  probably right, and if it is, this entry shrinks to four items.

Deliberately not in this entry: the binary's own boot wiring. `headless.rs` builds
the backend, and `main.rs` past that point is `slint::run_event_loop_until_quit`
