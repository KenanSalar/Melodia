# UI patterns — the shared components and what already exists

What to reach for instead of building a second one, and the two teardown paths that keep
the UI from pinning GPU buffers. This is the "reuse this" file; the things that *build,
look right, and are still wrong* are `.claude/rules/slint-pitfalls.md`, which loads on the
same globs.

A rule rather than a `CLAUDE.md` beside the code, for the reason the root file gives: UI
features cut across two trees (`.slint` under `melodia-ui/ui/`, Rust under `src/ui/`), so a
per-directory file would reach one and silently miss the other.

## Shared components

- **Tooltips via `Tooltip`** (`melodia-ui/ui/components/tooltip.slint`) — a plain absolutely-positioned pill, not a `PopupWindow`, so it captures no input and the host keeps its hover. Owns the 500 ms reveal delay and the fade; `side: TooltipSide.{above,below,left,right}` picks which edge it clears, and it takes `host-width`/`host-height` explicitly because a component root can't reach `parent`. **A variant is only half of a side** — the `x`/`y` ternaries fall through to the *centred* arm for anything they don't name, so a variant without its own arm puts the pill on the host rather than beside it, compiling and fading in exactly as before; `ui::placeholder_tests::the_tooltip_clears_its_host_on_all_four_sides` pins both halves. **Two mount shapes.** In-tree (`IconButton`, `PillButton`, the traffic lights, the swatch dots) is the default and works wherever nothing clips or overpaints the host. **Top-layer** is for hosts whose tooltip lands somewhere Slint paints later: a frame `Rectangle` declared after the occluder, tracking the host's rect via `absolute-position` deltas, with the pill inside it. **Six of those, in five files** — `my-library-view.slint` has two (`tab-tip` for the band's compact tab bar, and the `header-tip` that came off the retired `playlists-view.slint` with its action pills), then `favorites-view.slint` and `recently-played-view.slint`'s `tab-tip`s, `settings-view.slint`'s, and the collapsed sidebar rail's `sidebar-tip` in `app-window.slint`. Every one is a *band* whose pill would land in the scroll body Slint paints after it, which is why the count tracks tabbed pages rather than tooltips. **A third wrinkle, not a third shape:** the two volume popups anchor to a *point* — the slider thumb's centre — rather than to a box, so each mounts the pill inside a zero-size `Rectangle` positioned on the thumb and hands over `0px` for both host dimensions. They also drive it off **`force-shown` rather than `hovered`**: a value readout has to be up on the frame the drag starts, where the 500 ms reveal is for a label you linger for. That is the hook the trigger disc's keyboard-HUD tooltip already took, so all three volume readouts are now one pill — they were two hand-rolled 42×22 `Theme.surface2` badges a few lines from the real one, diverging from it in eight ways each and pinned now by `ui::placeholder_tests::the_volume_readouts_are_the_shared_tooltip`.
  - **The anchor may cross a component boundary, and there are now three answers to that, not one.** A frame can only read ids in its own file, so anything the tooltip's host doesn't own has to be published to it. `MosaicTabHero` and `LibraryTabBand` publish `tip-x` / `tip-y` / `tip-w` / `tip-h` / `tip-label` / `tip-visible` as `out` properties and the page spells five lines; the sidebar rail publishes onto `Nav` instead, because the boundary it crosses is a *component* the frame's file doesn't contain (below). **`views/my-library/tab-pills.slint` is the third, and the first where the boundary crossed is an `if`.** Its four Playlists-tab action pills carry `tooltip-overlay: true`, so the frame is `my-library-view.slint`'s and the anchor is a pill inside the pills component — and an id declared inside an `if` can't be read from outside it, so the row can't be `if`-gated at all. It collapses to a zero-width `clip: true` cell instead: nothing paints, and `Clip` swallows every event outside its empty rect, so the pills are as unreachable as an unmounted branch while their ids stay readable. Re-`if`-gating the row is a compile error rather than a silent regression — the `tip-*` bindings stop resolving — which is why the pin worth having covers the *other* half, that the sheet still draws the frame (`my_library_tests::the_playlist_action_tooltip_is_published_rather_than_drawn`).
  - **The rail's tooltip is the one that crosses a component boundary, and that's what makes its channel a global.** It mounts in `app-window.slint` after the whole `VerticalLayout` — the `Sidebar` is the content row's *first* child, so anything it painted past its own right edge would land under the content panel, and `nav-scroll` clips it besides. The hovered row publishes itself on `Nav` (`sidebar-tip-idx` / `-label` / `-y` / `-h`, with `sidebar-collapse-tip-idx` as the Collapse toggle's key, since it sits in the rail but owns no nav index): the rail's rows are ten hand-written mounts, so routing hover up through `Sidebar` as an `out property` would put a forwarding line on each. Nine of the ten reuse the row's own `@tr` label for free; the toggle is the exception and reads `@tr("Expand")`, because the tooltip only ever shows on a collapsed rail and its row label says the opposite. The **x** is the one thing not on the global — it comes off `sidebar.width` live, so the frame rides the collapse animation, and the 500 ms reveal outlasts that animation so the pill can't surface while the labels are still readable. Same retract rule as the tab bar: keyed on the index, so a leave arriving after the next row's enter can't blank a live tooltip. **The gaps are what the tab bar doesn't have, and they need a hold.** Rail rows sit 4 px apart with a `Divider` between some pairs, so a pointer travelling down the rail is over nothing for a frame or two; retracting on that restarts the 500 ms reveal on every row change and the pill flashes the new label, fades out and comes back. The frame keeps a `held` bool that a row's enter sets and a 150 ms `Timer` clears only once nothing has taken the hover, and `hovered` is `row-hovered || held` — the label and the frame's rect are untouched on retract, so the held pill sits still and swaps to the next name the moment that row takes over. The tab bar's edge-to-edge cells never drop hover in the first place, which is why it needs none of this. **`held` extends a tooltip and can't arm one**, which is why `row-hovered` is read beside it: `held` is written from a `changed` handler and `changed` doesn't fire on a first evaluation, so a rail that remounts with `row-hovered` already true would sit dead until the pointer left it once. **What makes it arrive already true is a sentinel nobody cleared, and that is the half that had to be fixed at the source.** `Nav.sidebar-tip-idx` outlives the rail, and the miniplayer swap destroys the whole full-UI branch with no unmount hook and no leave event for the row under the pointer — the same shape as the `CompositeScroll.reset()` obligation in `slint-pitfalls.md`, and the second instance of it. `changed watched-mini-render` now clears it alongside that reset. Without the clear, arming on `row-hovered` reveals a pill at the *stale* `sidebar-tip-y` with the stale label and no pointer near the rail, and it stays up until some row completes a hover/leave cycle; a new unmount path that strands the rail owes the same one-liner.
- **The multi-select trailer via `SelectionPills`** (`melodia-ui/ui/components/selection-pills.slint`) — the "{n} selected" label and the `close` button every list view's `ActionPill` grows once rows are selected, at eight of the nine sites that had it. **Mount it behind the host's own `if`, never with a count of zero**: the three slots are unconditional inside, so an unselected list mounts nothing at all, where a component hiding its own children would still occupy a cell and claim one `pad-xs` of the pill's spacing — a chip permanently a gap wider. That is also what retires the triple-spelled predicate each site carried, one `if` per slot. `divider-trails` follows position rather than taste (the separator always sits between this group and whatever shares the pill with it): six mounts put the group last and take the default, My Library's Songs tab and Browse put it first and set the flag. **Playlist Detail's row stays hand-rolled**, and deliberately — its group carries a destructive "Remove from playlist" pill *between* the count and the close, with a divider of its own and gated on the playlist not being smart, so absorbing it costs a children slot plus a `has-action` bool restating that same `is_smart` predicate at the mount.
- **Popup chrome via `PopupSurface`** — every `PopupWindow` body wraps `melodia-ui/ui/components/popup-surface.slint` (Theme.crust fill, 1 px Theme.surface2 border, Theme.radius-md, no entry anim). `pill: true` for vertical-pill.
- **A surface that floats over the app states its own edge with `Theme.surface2`, never `Theme.border`.** Four do — `Tooltip`, `PopupSurface`, the dialog card and the toast card — and three of them had drifted onto `Theme.border`, which **all four Catppuccin variants define as literally the same hex as `surface0`** (Mocha, both `#313244`). So a `surface0` card painted a border of its own fill and had no rim at all: the dialog read as a flat slab, and inside it `PickerListCard` and the mosaic grid were `surface0` cards on a `surface0` dialog with invisible edges, so their contents looked like loose rows floating on the dialog. `Theme.border` is still right for an **input field** (`LabeledInput`, `RuleValueInput`, `MultilineInput`), which sits on `surface1` and wants a darker outline rather than a lighter rim — that is the test to apply, not the element's kind: what is the fill underneath, and is the edge meant to lift the surface off its background or to recess a field into one.
- **Pill buttons via `PillButton`** (`melodia-ui/ui/components/action-pill.slint`) — 32 px outer / 28 px chrome, `Theme.surface1` hover. `danger: true` keeps that same chrome and only tints the icon **and** label to `Theme.danger` on hover — no permanent red fill, since Tauri's filled-red read as over-prominent for inline action rows. (The filled treatment is `SectionButton`'s, and it's the one that hover-lightens with `Theme.danger.brighter(10%)`; the two are not one pattern.) Compose inside `ActionPill` with `PillLabel`/`PillDivider`. **Sort-row pills** carry `reserve-sort-slot: true` + `sort-direction` — trailing 16 px `arrow_drop_*` slot. Never concatenate Unicode `↑`/`↓` into the label. `IconButton` for round controls *outside* chips.
  - **A sort row's Rust half is two shared helpers, not a hand-rolled block.** `ui::callbacks::next_sort(cur_field, cur_dir, clicked) -> (String, SortDir)` decides the pick (same field flips, a new one starts ascending) and `persist_view_sort(state, view_id, field, dir)` writes it to `views.json`; `persisted_sort` seeds the pills back at `wire_*` time. Eleven views had spelled the toggle out identically — four detail views, three entity grids, Tracks / Browse / Search / Favorites-Songs — and two of them re-derived a `SortDir` from a token they had just built. `next_sort` reads `cur_dir` the way `SortDir::from_token` does (**only** `"desc"` is descending), which the copies did not: they tested for `"asc"`, so an unrecognised token left that pill unable to reach descending. Unreachable today, and the sort of divergence that stops being unreachable the moment someone adds a third direction. Mounters: **`views/my-library/tab-pills.slint`**, which holds the Albums / Artists / Genres rows in one file, and **`favorites-view`'s Artists tab**; every other sortable surface routes the same pair through a `TrackList` column header instead. All four are now pinned against their comparators — `ui::my_library::tests::every_sort_pill_asks_for_a_field_the_comparator_knows` for the three, its `ui::favorites::tests` twin for the fourth — so a typo'd field token fails a test rather than silently sorting by the default arm while painting its arrow as though it worked.
  - **The Slint half is one component too: `components/sort-pill-row.slint`'s `SortPillRow`**, the `TabBar` shape (parallel `labels` / `fields` arrays plus a `request-sort(string)` callback), mounted at all four rows. It exists for what it makes *unspellable* rather than for the ~85 lines: each of the eleven pills used to spell `reserve-sort-slot`, a `sort-direction` ternary and an `active` comparison against its own field token, and any one of the three could go missing at one site and look right until the sort moved. Those three are now pinned once, against the component, by `ui::my_library::tests::the_sort_row_holds_every_per_pill_contract`. What the *mount* still owes is the two arrays lining up — a label with no matching field reads `fields[i]` past the end and sorts by the empty string, a pill that looks live and does nothing — so both pins check their lengths against each other, through the shared `test_support::sort_pill_row_arrays` parser rather than two copies of it. `labels` stays an inline `[@tr("…"), …]` literal at each mount, the usual reason.
- **Reusable grid + detail components.** Grids compose `EntityCard` in virtualized chunked-row `ListView` — Rust chunks flat list into `AlbumGridRow` of N; `GridColumnsSync` computes N from width, fires `columns-changed` for no-DB rebuild. Detail views own no header at all: the four under My Library are bodies, and the banner is the page's own `LibraryTabBand` morphing into it (below).
  - **A strip and a grid are different components on purpose.** `HorizontalCardStrip` walks its rows in a plain `for` inside a horizontal `ScrollView` — affordable for a capped carousel, and not for an uncapped page, where every card would be built and every cover requested. `components/grid/entity-card-grid.slint`'s **`EntityCardGrid`** is the vertical, virtualized counterpart over the same `EntityStripRow`, chunked into `EntityGridRow`s by Rust (`ui::grid_rows::chunk_entity_rows`). It carries `AlbumGrid`'s host-mounted-scrollbar contract verbatim (`v-visible-height` / `v-viewport-height` / `v-offset` / `set-v-offset`), plus the `covers-generation` one below. Three instances, one per grid tab: Favorites' Most Played and Favorite Artists, and Recently Played's Most Played. **Each replaced a capped carousel and dropped that cap on arrival** — `MOST_PLAYED_LIMIT`, `get_most_played_favorites`' `Option<i64>`, `get_most_played`'s `LIMIT` and its `.clamp(1, 100)` — because the reason for a cap is the strip's plain `for`, and a virtualized grid doesn't have one.
  - **The play-count badge lives on `EntityCard`** (`badge-text`), not on whichever host wants it — it moved off `HorizontalCardStrip` when the grid needed the same pill. It renders the count as a `Text` beside a `MaterialIcon { name: "play_arrow" }` rather than a `"▶"` in the string: a glyph Vazirmatn lacks pulls a fallback font whose taller metrics define the line box, which drops the digits off the patched centring. Shares the top-left artwork corner with `badge-icon`; no caller sets both.
  - **`GridGeometry` and `GridEmptyState` are the two pieces every grid page repeats.** `components/grid-geometry.slint` is non-visual (the `GridColumnsSync` / `FilterThrottle` shape) and turns `avail-width` + `min-card-w` + `gap` + `card-text-h` into `cols` / `card-w` / `card-h` / `row-h`; feed it the **body**'s width, whose value the layout fixes independently of the cards inside it, so a card sizing itself from it is a derivation and not a cycle. `components/grid/grid-empty-state.slint` is the centred glyph + heading + copy block — and **not only grids**: Browse's three states and Playlist Detail's empty list are the same block and mount it too, which is what its optional `action-label` / `action-icon` / `action-clicked()` exist for (Browse's two carry an "Open Settings" and a "Back" pill). Those are properties rather than an `@children` slot on purpose: an empty `@children` still occupies a cell and claims one of the column's `pad-md` gaps, shifting the vertical centring of every mount that wants no action, where a false `if` costs nothing — the same idiom the optional `body` already uses. **Every grid surface uses both** — the four hand-copied `min-card-w` / `computed-cols` / `card-w` / `card-h` / `row-h` blocks went when the entity grids became My Library tabs, and that swap was a fix as well as a de-dup: each copy computed off `grid.width`, the child it was sizing, where `GridGeometry`'s contract is the *container*'s. **My Library derives it once for four tabs**, since they are mutually exclusive and draw the same card: `views/my-library-view.slint` mounts one `GridGeometry { avail-width: body.width; }` and hands `card-w` / `card-h` / `row-h` / `gap` down to whichever tab is mounted, the `favorites/most-played-tab.slint` contract. The gutter lives on the sheet and is passed to both, because an `in` property isn't readable back from outside the component declaring it.
  - **Every grid's Rust half chunks through `ui::grid_rows::chunk_rows(items, columns, card, row)`.** A grid's `ListView` virtualizes by *row*, so the chunking **is** the virtualization boundary: a flat list becomes `ceil(n / columns)` one-field grid-row structs, each holding that row's cards as a nested `ModelRc`. Five surfaces do it and they differ only in the card type, the row type, and how a card is built — `card` is what absorbs that last one, so the four entity grids can chunk *indices* and project out of their `GridData` while both Favorites grid tabs chunk already-built rows, through the same call. `columns` is floored at one: a grid mid-layout can report zero, and one card per row is a visible wrong where a zero-width `chunks` is a panic. It sits beside `grid_prewarm` rather than inside it because nothing in it touches a cache — that module is the grids' shared *cover* machinery, this one is their shared *model* machinery. **The two curated pages take a shorter route: `chunk_entity_rows(rows, columns)` and `write_grid(model, rows, label)` live here too**, since their chunk is the same specialisation (`EntityStripRow` → `EntityGridRow`) and their write the same `set_vec`-or-log. Don't re-roll either at a new grid tab. **`write_grid` is generic over the row type**, which is what lets Browse's card grid use it too — it held a byte-for-byte copy for `BrowseCardGridRow` and said so in a comment, the row structs Slint generates all being plain data that satisfies the `'static` bound `downcast_ref` needs. My Library's four grid tabs are *not* on that route — they are the entity grids unchanged, still projecting out of their own `GridData` through the general form.
  - **The two mosaic heroes share their artwork square: `components/hero/mosaic-hero-tile.slint`'s `MosaicHeroTile`.** Favorites and Recently Played draw the same 140 px tile — the chrome-owning outer `Rectangle` (fill, 1 px `tile-edge`, `radius-lg`, `clip`) over either a centred empty glyph or a flush-fill `CoverMosaic` — and differed in exactly three values plus the cover callback, so the tile takes `count` / `paths` / `empty-glyph` and each view keeps its own mosaic tier. **Every brush in it is a `HeroBackdrop` tier and none may become a `Theme.*` token**, both sides of the ternary: with no mosaic the hero is the dark gradient floor where a light theme's accent lands dark-on-dark, and the populated fill matters just as much because the mosaic's placeholder slots are translucent — whatever fills the rectangle is most of what their chrome composites against. Its `request-cover` is `pure`, because `CoverMosaic`'s is. It is now mounted **once**, by `MosaicTabHero` (below), which forwards each page's three values and its callback — extracting it was the first step of extracting the whole band, and it stays a component of its own because the square is the one part of that banner a non-tabbed hero could want.
- **Metadata chips via `MetaChip` + `MetaChipStrip`** (`melodia-ui/ui/components/meta-chip{,-strip}.slint`). A chip is a 26 px stadium with `pad-md` side padding and a `font-size-sm` label — decorative only, no `TouchArea`, no selected state. The *interactive* pill is `components/settings/chip-group.slint`'s `Chip`, and the two are deliberately not one component: one states a fact, the other configures something. Both of `MetaChip`'s brushes are defaulted `in property`s, the `TabBar` shape, and **every mount overrides both** — Now Playing passes the `np-accent-{pill,bright}` pair by hand, and the six heroes take theirs through **`components/hero-chip-strip.slint`**'s `HeroChipStrip`, which fixes `HeroBackdrop.chip-fill` / `chrome` and forwards `measured` into `HeroChips.recompute`. That wrapper is where a hero mount belongs: the four bindings were identical at all six, only one hero is ever on screen, and fixing them makes the wrong mount unspellable rather than merely tested against. **It also owns the one knob a *morphing* hero needs — `fade`, multiplying both brushes** (default `1.0`, so the five fixed heroes never name it). Only `LibraryTabBand` sets it, and it has to fade this way rather than with an `opacity`: the strip carries `MetaChipStrip`'s `changed watched-w` tracker, so a band wanting a fade-out has to keep it *mounted* across the collapse instead of dropping it mid-animation (the change-tracker entry in `slint-pitfalls.md`), and `Opacity::need_layer` bails only at exactly `1.0` — a permanently mounted subtree at any other value blends an offscreen layer every frame, forever. The pill goes through `HeroBackdrop.chip-fill-at(fade)` rather than a local `with-alpha`, because `with-alpha` *sets* alpha instead of multiplying it and a local spelling would have to restate the tier's own weight. **A second float rides beside it, and it is the wrapper's own: `arrive-t`, eased on `dur-med` off `rows.length > 0`.** The chips are the one hero fact that can land *after* the banner — a My Library tab re-entered onto an open detail morphs its band open on artwork and colours held for it while these are still behind the re-fetch that folds them — and stepping them in beside a band that has already settled reads as a glitch. `dur-med` because that is what the blur crossfade and the four palette mirrors either side of them already take, so the band settles as one thing rather than gaining a part that snaps; it was `dur-fast` on the argument that the point of a chip is that the number is *there*, which is right about the wait and wrong about the weight. Both brushes carry both factors; multiplying only one fades the pill while its label steps, which reads as a rendering bug. Safe to `animate` as a binding where a host-supplied brush is not, since its only dependency is the row model, which Rust writes discretely and `write_rows` leaves alone when the chunk shape hasn't moved. All six heroes inherit it. Pinned by `ui::library_tab_band_tests::the_chip_row_fades_in_when_it_lands`. The `Theme.*` defaults are correct nowhere and are never taken; they exist so the file imports neither `Player` nor `HeroBackdrop`, which is the whole reason one component can sit on a blurred cover *and* a blurred banner. `MetaChipStrip` owns the row layout plus both paid-for pitfalls (the `watched-w` mirror, since `changed` rejects a path expression, and the 1 ms mount seed, since it doesn't fire on a first evaluation) and reports through `measured(length)`; **who chunks, and how far overflow may wrap before being dropped, is the host's**, via `ui::chips::chunk_chips_to_rows`'s `max_rows` — `None` for the Now Playing column, which has the height to grow, `Some(HERO_MAX_ROWS)` for a hero band, which does not. **That constant is 2, and the 2 is measured rather than picked**: every hero ends its meta block with a `Rectangle { vertical-stretch: 1 }` before the action pill, and a second 26 px row plus its 4 px gap fits inside that slack on all six — so a narrow window wraps into space that already existed instead of losing a chip, and the band holds still. `LibraryTabBand` reserves the pill row as a `padding-bottom` on that column rather than as a child of it, because its pills float in a slot riding the animated height; the slack the two rows are measured against is arithmetically the same either way, which is the point of spelling it that way round. **The gap is `pad-xs` between rows and `pad-sm` between chips**, and only the horizontal one is mirrored in Rust (`ui::chips::SPACING`); a wrapped row is the same strip continuing rather than a second one, so the tighter vertical gap reads correctly *and* is what buys the fit. **The two heroes carrying a second text line are the ones that had to be argued for** — Album's artist and Playlist's description — since their band is `Theme.hero-artwork` plus padding and nothing else. Under `DetailHeader` that line rode *inside* the title row, where the `SearchBar` beside it had already claimed the height; **in `LibraryTabBand` there is nothing to ride in**, the search box having moved up into the tab row, so it is a sibling row costing its own line box plus a `pad-xs` gap. What buys that back is that four heroes now share **one** subtitle row instead of each spelling its own, so the arithmetic is stated once and checkable: the meta column is `Theme.hero-artwork` less the pill band it reserves — 140 − 36 = 104 px — and a subtitled hero at two chip rows lands right at that ceiling. Raising either half of the `Theme.hero-title-size` + `font-size-md` pair those rows are stacked from is what breaks it now, not moving the line. If a wrapped second chip row ever clips on Album or Playlist, the fix is a per-hero max into `ui::hero_chips::write_rows`, **not** a taller band — the band clips, so the failure is bounded. **`hero-title-size` is also the one number all six titles read**, the `hero-artwork` argument applied to type: they had already drifted to two sizes (four detail views at 24 px, two mosaic heroes at 28 px) with nothing recording which was intended, and a literal is invisible in review because each view reads correctly alone. Two shared bands is what makes that a two-file property rather than a six-file one. A third row overruns the tile on all six and pushes the pill out of the banner, which is why it isn't `None`. **That whole argument is load-bearing on the strip's rows hanging off a plain `VerticalLayout` rather than off the root, and on that wrapper pinning `min-width: 0px`** — the `if`-conditional-child pitfall in `slint-pitfalls.md`, which cost this component two shipped bugs, one per axis. Without the wrapper the root reports `preferred: 0`, takes its 26 px `min-height` as its whole allotment, and paints the second row outside it, so `max_rows` bounded a wrap that never happened. *With* the wrapper and without the `min-width`, the widest published row becomes a floor no narrowing can negotiate, so the strip keeps being handed — and keeps reporting back — the width it was chunked at, and the row clips against the panel edge instead of wrapping; `HERO_MAX_ROWS` was then reachable only by *mounting* narrow, never by dragging there. The second is the one to keep in mind, because fixing the first is what introduces it. `ui::hero_chips::tests` pins the eight things a refactor breaks silently: that every band mounts `HeroChipStrip` rather than reaching past it, that it and the Now Playing mount pass both brushes, and that `MetaChip{,Strip}` still import neither hero nor player globals — the layering the defaults exist for; that no hero still declares the meta-line property the chips replaced, that the strip keeps its mirror and its seed, that its rows still hang off a layout, that the layout leaks no width floor, that the row gap stays tighter than the chip gap, that the four subtitled heroes share one collapsing line, and that every title reads `Theme.hero-title-size`. **`HERO_VIEWS` is two entries, for six banners**, and the arithmetic is worth stating: each band stands for the pages under it — `mosaic-tab-hero.slint` for Favorites and Recently Played, `library-tab-band.slint` for the four details — so there are two files to hold to the contract rather than six that can drift. Two further arrays pin the other half, that a page still *mounts* its band and has grown no title, chip strip or artwork size of its own: `MOSAIC_HOSTS` over the two curated view files, and **`BAND_HOSTS`** over `my-library-view.slint` plus the four detail bodies. The bodies are the half worth pinning — a detail regrowing a header of its own passes every other check in the file, because the shared band it stopped using is still correct.
- **Detail-page TrackList inset — and half of it stopped being necessary when the header left.** The rule was that a detail's root `VerticalLayout` couldn't pad, because `DetailHeader` was full-bleed for its hero blur, so each wrapped its `TrackList` in a `HorizontalLayout { padding-left/right: Theme.pad-lg }` to match `views/my-library/songs-tab.slint` / `browse-view.slint`. The band is full-bleed now instead, so a detail *body* is free to inset on its root like any grid page — **Album and Genre did; Artist and Playlist still can't, for reasons of their own.** Artist Detail's `below-hero` is the region `CompositeScrollbars` measures and the `CompositeScroll` hover sentinel covers, so it has to run full-bleed; Playlist Detail's empty state and drop banner deliberately fill `body`. Overlay scrollbars stay at `parent.width - self.width` (root-relative) either way. Bottom padding is still never on the root — see the dead-strip entry in `slint-pitfalls.md`.
- **`play-row` replaces the queue with the view; there is no single-track play path, and no Play-All pill either.** Every row activation resolves the view's *displayed* ids and hands them to `library::playback::player_play_tracks(ids, start)`. Each of those folds its **own** answer on its **own** worker, from the `Vec` it just awaited, and stores it (`FavoritesUiState::songs_fold` / `::most_played_totals`) before calling `hero::republish_chips`. `publish_favorites` then reads finished `Copy` values, so the worst a mistimed publish can be is a tick stale rather than half-built — where folding at publish time meant the band came up with two chips at cold start and gained the rest only on the next visit, having walked every favourite on the UI thread to get there. The grid write can't stand in for the republish twice over: `write_filtered_grids` publishes *past* a signature early-return, and `mounted_content` is a constant `0` on the Songs tab, so there it fires only when the column count moves. `ui::hero_chips::tests::each_favorites_fetch_folds_and_republishes_what_it_feeds` pins the fold and the republish into the same function as the fill, and `…::no_hero_folds_out_of_a_shared_cache` pins that no publisher folds a `.lock()` — `hero_chips.rs` is itself in that list, since it holds the handle and every cache is one `.lock()` away. **Moving the fold onto the worker moves the teardown with it**, which is the half easy to miss: `release_section_state` resets both folds beside the caches they summarise, because a derived value outliving its source is the one thing the band can state that is *wrong* rather than merely absent. Folding at publish time hid that — the fold read a cache that **was** cleared, so it degraded to no spread chips. Stored, it survives the leave, and since `refresh_hero` is the shortest of the three fetches it publishes first on the re-enter and pairs a fresh count with a pre-leave spread: "3 favorites · 37 artists", until `refresh_tracks` lands. `…::the_section_leave_drops_the_folds_with_the_caches_they_summarise` pins it.
  - **A band states facts about the set the page is about, never about the current filter.** Forced rather than chosen: an album's chips cannot follow its track filter without lying about the album, so the alternative rule would hold on two heroes out of six. The counts that *do* track a filter already exist and already do — `Favorites.most-played-count` / `.artist-count` gate the grids' empty states, and reusing one for a chip is what made the Artists tab renumber under a keystroke while its two siblings sat still.
  - **Those counts hold `-1` until fetched, and a section leave puts them back** (`ui::tab_bar::UNFETCHED_COUNT`, written **beside the model clears** in every leave arm that has one — both curated `lifecycle.rs` files and the four entity grids'). A count outliving the model it numbers is the same "derived value may not outlive its source" rule the hero folds follow, and here it suppresses an empty state over a model the leave just emptied — while resetting to `0` instead asserts "No favorites yet" for the whole length of the re-fetch, which on a Most Played tab waits on a cover-decode burst. `-1` matches neither `== 0` nor `> 0`, so every gate keeps the expression it already had and simply says nothing until there is an answer. **The one reader that must know is `MosaicHeroTile`**, which splits on *both* comparisons and so renders neither glyph nor tiles in between: its two mounts clamp with `max(…, 0)`. That was the visible half of the bug — a stale non-zero `track-count` over an emptied `mosaic-paths` drew four placeholder slots where the square should have shown its empty glyph. A new count on either global inherits the sentinel; a new reader that splits on both comparisons owes the clamp. `ui::tab_bar::tests` pins the declaration, the leave-reset and both clamps, over `CURATED_PAGES` and `LIBRARY_PAGES` alike. **The five library counts adopted it when they started gating shared chrome**, which is what forced the one thing the curated pages never needed: each is interpolated into a gettext plural, so a bare `-1` renders "-1 albums". Every one of them is now read through a `>= 0` ternary — five in the band's one `count-text`, a ternary rather than an `if` so the `Text` keeps its slot and nothing jumps — and that guard is not optional at a sixth. **Tracks is the exception, and the exception is the rule read precisely**: what obliges the rewind is the leave dropping the rows, and its leave doesn't — `TracksUi` has no `release_section_state`, and the Songs leave touches neither `Tracks.rows` nor the cached `full` Vec, so the count stays true for as long as what it numbers is on screen. It briefly took the full arm anyway, and that is the shape to not restore: a rewind is only honest beside a `mark_dirty()` (nothing else re-fetches this list, so the count would otherwise read `""` over rows still there, permanently), and marking dirty on a *tab* leave made every return to Songs a full `get_tracks` plus a library-sized row build on the event loop — for a list that had never gone anywhere. Both went together because neither was load-bearing without the other, so both went. `ui::tab_bar::tests::every_library_leave_rewinds_the_count_it_numbered` pins the split through `LibraryPage::rewinds_on_leave` rather than allowing either shape. The two halves stay coupled at a sixth page: **rewind if and only if you clear**, and if you clear, mark dirty. **A leave is no longer the only thing that clears, which is where the rule earns its "if and only if".** A *tab pick* runs a synchronous apply against whatever cache is there, and on both tabbed pages that cache can be one the leave (or a skipped refresh tick) emptied — so the apply writes `0` over the sentinel the leave wrote, and the panel asserts an empty library for the length of the fetch that is already on its way. Two sites therefore rewind on the pick as well: `my_library::filter::clear_mounted`, past the dispatch it only makes when the entering tab is genuinely filtered (`rewind_grid_count`, excluding Songs, whose model survives the leave, and the four details, which write no grid count), and Recently Played's `on_tab_changed`, when `take_grid_dirty` says the grid fetch it is spawning is the one that will answer. The band goes quiet with the count in both cases, chips being published off totals that are zero too — which is the "an empty hero states nothing" shape, and the right one while there is no answer.
  - **The facts a stats row doesn't carry are folded on the worker, never in the closure** — `ui::hero_folds`' `fold_tracks` (distinct artists / albums), `dominant_genre`, `year_span` and `fold_most_played` all run beside the fetch that produced the `Vec`, and their `Copy` results ride into `upgrade_in_event_loop`; a broad genre's track list is the longest in the app and has no business being hashed on the UI thread. **Most Played sums itself**, which is the one arithmetic trap here: its query is `is_favorite = TRUE AND play_count > 0`, a strict subset of the Songs tab, so reusing the Songs duration would overstate it by every favourite never played (`most_played_sums_itself_and_not_the_songs_tab` pins it). A spread of one is stated as nothing at all — "1 artist" over a single-artist list is noise, so `push_fold` gates both chips on `> 1`. **A set of *none* is stated as no band at all**, for the same reason one step further out: an empty hero publishes zero chips and leaves the copy to whatever the body already paints — a sentence on the Songs and Recently Played heroes, a `GridEmptyState` on the two Favorites grids — so no page says "nothing here" twice. All three Favorites tabs gate on it, and each gates on the *unfiltered* count, since a filter matching nothing is the empty states' business and not the band's (`an_empty_hero_leaves_its_empty_state_to_the_view` pins all four surfaces).
  - **The two mosaic heroes' `last_mosaic_paths` guard means "this mosaic is what's painted", so it moves only *past* the check that decides whether anything is** — inside `hero::apply_hero_blur` and `hero::clear_hero_blur`, never at the fetch that kicked them. **Those two are one source, not two**: `src/ui/mosaic_hero.rs`'s `impl_mosaic_hero!($Global, $Ui)` generates the pair into each view's `hero.rs`, so the guard placement argued here is stated once and each view keeps only the comment saying how reachable an overlapping compose is on its side. A macro rather than a generic fn for the `impl_detail_view_helpers` reason — `Favorites` and `RecentlyPlayed` are distinct Slint-generated globals that happen to declare the same `blur-img-{a,b}` / `blur-use-a` / `has-blur`, with no trait between them. Both of those bail outright when the section went inactive mid-compose (see above — one global, six heroes), so a guard written beforehand records a paint that never happened: every later refresh for the same top-4 then early-returns, and the banner sits on the accent-seeded gradient floor with the tab bar taking `HeroBackdrop.chrome` from it — for the rest of the session, since only a section-leave's `forget_mosaic` clears it. It reads as an intermittent cold-boot glitch that a nav-away-and-back "fixes", and **only the hero is wrong**: the stats, the mosaic tiles and the grids all land, because none of them sits behind that guard. Recording past the check costs a duplicate compose per refresh that starts inside the compose window, since none of them has a record to skip on yet; the losers re-check under the same lock and drop out rather than re-fading an identical buffer. **The two views differ in how reachable that is.** Favorites self-serialises — `refresh_hero` awaits its own `spawn_blocking` and the `library_changed`/`stats_changed` subscriber awaits `refresh_hero`, so two ticks can't overlap; what can race one is the **section-enter** fetch, spawned detached by both the first-enter kick and every re-enter after it. Recently Played does not: `songs::refresh_tracks` spawns `refresh_blur` **detached**, so the subscriber loop is free to come round again and re-read a guard nobody has written, once per tick. Bounded in practice by the `get_recently_played` + full-capacity cover prewarm every tick pays first, which is why it's a cost worth naming rather than a debounce worth rebuilding. Recently Played is also the one that needs the *clear* half most, since `refresh_tracks` only calls in when the paths differ from what the guard holds. **Its mosaic ranks by recency, not by its Most Played tab**, which is the one place the two pages' bands genuinely diverge: Favorites' tiles are the head of the Most Played walk, so the banner leads with the tab beside it, where a "Recently Played" banner ranked by play count would name the wrong page. This is the `last_grid_signature` discipline (write where the paint happens) applied to the one guard that wasn't following it; `forget_mosaic` stays the single exception, and it exists because the section-leave wipe is unconditional where `release_section_state` is not.
- **Now-Playing accent tiers are derived on the `Player` global, not at the call site.** One solved brush (`np-accent-bright`) plus three named translucent tiers off it — `np-accent-pill` (.16), `np-accent-disc-hover` (.30), `np-accent-dim` (.60) — following `melodia-ui/ui/theme.slint`'s `floating-chrome-bg` precedent. Reach for the tier, never a fresh `.with-alpha(…)`: the same alphas were spelled out across six files, so two surfaces meant to match could drift with nothing failing. `np-accent-pill` is the resting weight for **every** tinted surface in the view — the metadata chips and the two `AccentDiscButton`s (back, view menu) alike — so the top bar sits at the same tint as the chips under it. Only alphas used **twice or more** earn a name; a genuine one-off (the Up-Next divider, its scrollbar's hover) stays inline, since naming it would move the number without sharing it. `np-accent-disc-hover` is the deliberate exception — a single reader, but that reader is `AccentDiscButton`, which is *itself* the shared surface, so it is named alongside the others and reads as one ladder of weights rather than as a rule and an exception.
- **Every filter box answers "does this row match" through `src/ui/row_match.rs`, and none of them spells `to_lowercase().contains(…)`.** The module owns three things: `search_fields` (the six fields a track row is searchable by, ordered like the `tracks_fts` column list it mirrors — title, artist, album artist, album, genre, plus `year` through `Needle::matches_year`), the `push_folded` / `fold_needle` pair that folds case **and accents**, covering everything that index's `unicode61 remove_diacritics 2` tokenizer folds, and the predicates over them (`track_matches`, `most_played_matches`, and `Needle`'s own `contains` / `equals` / `starts_with` for the single-name surfaces — the last two exist for the Search view's Top Result ranking, which asks *is this the name* rather than *does it contain the name*, and which ranked on a bare `to_lowercase` until it did: `bjork` filled the Songs list and both strips through FTS while the card fell through to its first-album-in-results fallback). Sixteen filter surfaces route through it: the four detail pages — **Artist Detail twice**, its track list and its Albums strip — Favorites' three tabs, Recently Played's two, Tracks, the four entity grids, and the Settings page. On all three tabbed pages the needle is **one shadow shared across the tabs**, and a tab pick clears it on both sides — the Slint property so the box doesn't hold text the page is no longer filtered by, and the Rust one so the entering tab's model isn't built against it.
  - **Nine of those sixteen are fed by a single box, and the hand-off is a Rust dispatch rather than a binding.** My Library has one `SearchBar`, in the band, whose meaning follows the mounted tab and any open detail; `src/ui/my_library/filter.rs::dispatch` routes a settled keystroke to whichever of the nine surfaces is up. It has to be a *write* — an element can't declare a binding on another global's property, so `Tracks.filter: MyLibrary.filter` is not spellable in Slint, and the only form that would be spellable puts `MyLibrary` in five globals' import lists. **The two contracts stay different underneath**: the five grid/list globals fire `apply-filter(text)` and Rust ignores the argument, reading `<Global>.filter` back inside a memoized rebuild, while the four detail globals fire `filter-changed(text)` and Rust uses it. All nine arms therefore `set_filter` before invoking — which is also what keeps `playlist-detail.slint`'s `reorder-enabled` honest, that being the one live *Slint* reader of a detail's `filter`. And because one box now describes nine surfaces, **opening or closing a detail changes what it means with nobody typing**: `MyLibrary.detail-scope-changed()` routes to `filter::sync_box`, the same hand-off read backwards, taking the newly-mounted surface's own filter. That is a *reseat*, deliberately not the tab pick's clear-both-sides — clearing on the way out would drop the user's grid filter on every back, which the old two-box arrangement never did. **A tab move fires it too, and that mirror is the one easiest to leave out.** `dispatch` clears only the *entering* tab's needle — it matches on the tab the bar has already moved to — so the departing tab keeps its own, which is correct and invisible as long as every arrival is a pick. The two arrivals that aren't go through `persist-tab-idx` (a cross-tab drill, a Mouse-4/5 walk) precisely so they *don't* clear, and there the tab's own needle is still in force with nothing having told the box: `nav_history` walks back into a Songs list still filtered by it — whether that list survived the leave or is re-fetched through the same shadow — and the box reads empty over a subset. So `my-library-view.slint` mirrors `MyLibrary.tab-idx` alongside the four detail ids and fires the same callback; a pick is unaffected, having cleared both sides before the change-tracker pass runs, so `sync_box` finds them equal and bails. All five mirrors are pinned by `my_library_tests::a_drill_a_back_or_a_tab_move_reseats_the_shared_box`. **The mirrors can't cover a re-open, which is the third caller and the one with no edge to fire on.** `open_*` clears its detail's own filter on every fresh open, and a **section re-enter** re-runs it writing the *same* id back — so nothing announces that the list under the box was just unfiltered, and a nav-away-and-back over a filtered detail comes up unfiltered under a box still holding the needle. Each of the four therefore invokes `detail-scope-changed()` itself, as the **last** statement of its `upgrade_in_event_loop` closure: `sync_box` picks the surface off the live id and tab, so anything earlier — beside the `set_filter("")` it is fixing, say — answers for the grid the detail is still sitting over and hands a fresh drill the bug the re-enter just lost. `my_library_tests::a_fresh_open_reseats_the_shared_box_after_it_writes_the_id` pins both halves. **It is the looser of the two folds on purpose, and years are looser still in the other direction.** `is_combining_mark` is `General_Category=Mark`, so the fold also drops the spacing marks of Indic scripts and the kana voicing marks where `SQLite`'s table is Latin-scoped — which only ever *widens* a substring filter, never hides a row a query names, and under-folding is the failure that shows. `Needle::matches_year` goes the other way: it is a **substring** where the FTS side's uniform `*` suffix makes years a prefix search, so `98` narrows a filter box to the 1980s and 1998 while `98*` matches no year at all. That is the field falling in with its neighbours — every other one matches mid-word — rather than with the index, and it is the one place the parity claim doesn't hold. **The reason it isn't per view is that the per-view boxes are a second answer to what the Search view answers with SQL**, and they were a narrower one — title/artist/album, compared literally — so a genre or a year found nothing in a filter box while the Search view found it. **A needle is folded exactly once, by whoever owns it — and `Needle` is what makes that a type rather than a comment.** `fold_needle` is the only constructor and the predicates take nothing else, so an unfolded needle is now unspellable; it used to be merely wrong, and silently, since the row side is always folded and an unfolded needle still matches, just without accent parity, on that one surface. The four detail views and both curated views store one at write time in their `set_filter` (so every reader of that shadow shares it), Tracks and the grids fold at read time and hold it for the length of one walk. Carrying the needle rather than a `&str` is also what lets its *shape* be answered once per walk instead of once per row: `ascii` decides the allocation-free byte path and `digits` gates the year rule, and neither can change between rows — both were being re-derived per field, per row, over the largest lists in the app. **Tracks is the one matcher that doesn't call `track_matches`**: its list is the largest, so `RowSearchKey` folds `search_fields` once per fetch into a packed `\0`-joined `Box<str>` a keystroke can `contains` without allocating (through `Needle::as_str`, which exists for exactly that one already-folded haystack), keeping `year` beside it as an integer so both matchers run the *same* `Needle::matches_year` rather than two spellings of it. `ui::tracks::tests::the_packed_key_and_track_matches_agree_field_for_field` pins that seam. **The entity grids match their raw fields, not their `*_lc` sort keys** — folding can't be baked into a plain lowercased string without also changing the sort those keys drive, and `Needle::contains`' ASCII fast path means an unaccented name costs the same byte walk either way.

## Covers

- **No row struct carries a decoded cover; every one of them asks for it.** `TrackListRow` has no `image` field, and `TrackListRowItem` resolves its thumbnail per *instantiated* row through `RowCovers.request(artwork_path)`, wired once in `boot/ui_setup.rs` to the shared row-tier `CoverThumbs`. New TrackList consumers need zero cover plumbing. `CoverThumbs::prewarm` dedupes input and caps work at LRU capacity — pass paths in **display order** so the kept prefix paints first. **`QueueRow` follows the same contract through two globals rather than `RowCovers`**, because each wants a different tier: `Queue.request-cover` reaches the queue sheet's *private* `CoverThumbs` (so closing the sheet can drop every buffer without yanking covers the track lists still need), `NowPlaying.request-cover` the shared row tier. That shape is what makes a queue the size of the library affordable — an eager cover meant one cache lookup per queued track on every queue emit, and the whole view goes into the queue on any row activation.
  - **`Queue.request-cover` takes a second `generation` argument, and it is the one place needing an explanation.** A `pure` callback's result is cached until a dependency is dirtied, and every other lazy-cover surface prewarms and **awaits before** it sets rows, so its first evaluation is already a cache hit. The sheet can't: its rows must land synchronously inside `on_open_changed` for the slide-up to have text on frame one. So the argument does two jobs — reading it is what makes the binding depend on `Queue.covers-generation`, and its *value* is the "is this tier warm" flag. **At 0 the Rust side answers cache-only** (`get_cached_opt`, the sole caller), so the rows the `ListView` mounts on that first frame paint placeholders instead of each dragging a decode onto the UI thread mid-animation — the sheet's tier is private and cleared on close, so every open is cold and every visible row would miss. The sheet then warms `QUEUE_PREWARM_AHEAD` covers off-thread and bumps, which re-runs the bindings *and* switches later rows to `get_or_load_opt`; the close teardown rewinds it to 0 beside `queue_covers.clear()`, so 0 keeps meaning "cold" rather than "first open of the session". Wire the decoding lookup unconditionally and the counter becomes dead weight — by the time the bump lands every mounted row already decoded, on the UI thread, which is the bug this shape exists to prevent. **Prefer the prewarm-then-set ordering** and copy this only when something genuinely warms behind a mounted list's back.
  - **`EntityCardGrid` is the second such surface, and a tab switch is what puts it there.** Every other grid enters through a fetch, so it can await its prewarm and hand the rows over warm; a tab pick has no fetch to hide behind — `TabBar` writes `selected-index` before it emits `selected`, so the `if` that mounts the entering grid is already true when Rust hears about it, and there is nothing to await *before*. The tier is cold every time besides, since tab-leave releases it. So the grid takes the same pair: an `in property <int> covers-generation` the card binding **reads** (`cover: root.request-cover(entity.artwork_path, root.covers-generation)`) and the host forwards into its page's `request-*-cover(path, generation)`. `on_tab_changed` writes 0 synchronously, `swap_tab_covers` warms off-thread, and the bump is gated on **two** answers — the prewarm's own verdict and a re-check of the `active_tab` shadow **on the UI thread**. They are separate because they fail separately: a *pick* made while the decodes ran has already rewound the counter and owns a different tier, while a section *leave* landing mid-decode makes `prewarm_tab_covers` hand its buffers straight back and return `false`, leaving the same tab correct and empty. Announcing either puts the next surface's cards straight back on the decoding path, which is the state the counter exists to prevent — so **a prewarm that may release what it warmed owes its caller that `bool`**, and the caller owes it the check. **The section-enter path takes the same pair** (`ui::tab_bar::should_announce_warm`, called from each page's `apply_filtered_grid{,s}`, fed a `warmed_tab` that is `Some` only on `Ok(true)` — a `JoinError` is the same "we don't know"): whether the tier is warm and whether the rows moved are independent facts, and gating the bump on the write conflated them. `write_filtered_grids` returns early both when the section is hidden — where the bump would be wrong — and when the signature is unchanged, where it is exactly what has to happen; a re-enter reliably hits the second, because the view's mount-time `columns-changed` writes the final rows while the prewarm is still decoding, so the apply that carried the announcement arrived as a no-op repaint and every card sat on a placeholder until the next tab pick. A new surface that warms behind a mounted list owes the same split: announce on the warm, not on the write. The hero's `CoverMosaic` keeps the one-argument form on purpose: the mosaic tier is warmed by a fetch, not by a tab. The property lives on the component rather than the host, which is what let Recently Played's Most Played tab inherit the whole contract unchanged when it stopped being a strip.
    - **`BrowseCardGrid` is the third such surface, and the third distinct reason.** The sheet's excuse is a synchronous open, the grid tabs' is a tab pick; Browse's is a **mode toggle** — the pill re-presents the cached listing with no fetch anywhere in the path, so `on_toggle_view_mode` writes 0, rebuilds the model **without hopping the event loop** (`invoke_from_event_loop` posts even when called from the UI thread, and a redraw winning that race paints an empty grid), warms a screenful off-thread and bumps, gated on the view still being where the prewarm left it. Its fetch path is the ordinary prewarm-then-write one, so the counter only ever moves *up* there. **What the tier's release obliges is a `mark_dirty()` on the section leave** — the Browse bullet in the root `CLAUDE.md`, and the general rule this file's own "a prewarm that may release what it warmed owes its caller that `bool`" is the other half of: a released tier is only honest beside a fetch that will re-warm it, and Browse has no enter-time fetch of its own. The same seed goes in at wire time (`if !section_active() { mark_dirty() }`), because the boot pre-fetch runs off-screen and `warm_card_tier` hands its buffers straight back. **The Rust half of the lookup is `ui::grid_prewarm::grid_cover(thumbs, path, generation)`** — the tier and the counter differ per page, the branch doesn't, so the three grid tabs share one copy rather than each spelling out the `get_cached_opt` / `get_or_load_opt` split. Reach for it at a fourth: a copy that grew a decoding `else` arm reads correctly and quietly retires the whole mechanism.
- **Grid-cover cache cap via `ui::grid_prewarm::cover_cap_for_window(app, fallback)`.** One band for every grid — they all draw the same card at the same size, so there is nothing per-entity to tune. Derives a `[32, 96]` cap from the current monitor's *logical* resolution (≈1080p → 35, 1440p → 54, 4K → 96) against a ~260×320 px card footprint, with one partial row of scroll headroom and no further cushion. Each cache is constructed with its own `DEFAULT_GRID_COVER_CAP` and resized from `install_views` once the winit window is live; the fallback is passed in so a module keeps ownership of its own default and a monitor that reports `None` (some Wayland setups) lands there. It had been copied verbatim into `albums`, `artists` and `playlists` — three copies of the footprint constants, the clamps and their tests — so the Favorites tabs would have been a fourth; extract, don't copy. The pure half is `cover_cap(w, h, fallback)`, pinned once by `ui::grid_prewarm::tests::cover_cap_clamps_and_scales_with_resolution`.
- **Cover-prewarm path dedup via `ui::grid_prewarm::unique_artwork_paths(paths, cap)`.** One shared `pub fn` turns an iterator of `Option<&str>` artwork paths into a first-seen-ordered, deduped, non-empty `Vec<PathBuf>` for `CoverThumbs::prewarm`. **Every prewarm site in the tree goes through it** — the four entity grids' and the three grid tabs' `first_screenful_paths`, the four detail prewarms, the Tracks / Favorites-Songs / Recently-Played-Songs fetches, the Recently-Played hero's own `mosaic_paths_from`, Browse's two (the row tier at full capacity, the card tier at a screenful) and the queue-sheet open — and the per-entity wrapper owns only the projection. Don't re-roll the dedup loop; reuse the helper, and don't lean on `prewarm`'s own internal dedup as a reason to skip it (Search and Browse each did, and each grew a divergent copy: Search deduped nothing and passed `PathBuf::from("")` straight to the decoder, Browse hand-rolled the loop uncapped). Search is the one call site with three of them, since its rows and its two strips land in three different tiers and each is capped against its own. **`cap` bounds kept *paths*, not input items**, so a grid passes `GRID_PREWARM_AHEAD` instead of `.take(N)`-ing its entity iterator and a full-list prewarm passes `cover_thumbs.capacity()`. It exists because `prewarm` truncates at the LRU capacity anyway: uncapped, a detail view over a 20 000-track genre allocated a `PathBuf` per unique cover to keep 512. Capping the *input* buys one thing beyond the allocation, and it's the reason to pass a cap rather than `usize::MAX`: `prewarm`'s own `.take(cap)` sits **after** its already-cached filter, so over a partially warm tier it will decode up to a full capacity of new paths from anywhere in the list — evicting the warm, visible prefix to do it.
- **Albums sub-section borrows `AlbumsUi.grid_covers`.** Artist Detail's Albums strip routes `request-album-cover` to `albums_ui.grid_cover(path)`. `wire_artists` releases on **both** Artists section-leave and `on_close_detail`.

## Releasing what the UI pins

- **Detail-close releases global Image properties.** `release_detail_hero_images!` resets `cover` + `blur-img-a/b` to `Image::default()`, clears `has-blur`, and re-solves the two shared globals (`hero_backdrop::reset`, `hero_chips::clear`), alongside `clear_detail` + `release_detail_artwork`. Without it, `SharedPixelBuffer` Arcs pin (~650 KiB CPU + ~1.5 MiB GPU on Mesa). It runs on each view's **section leave** — but since the My Library fold that fires on a tab switch too, and a tab switch is not a teardown, so each half of the macro is gated: the slots and the colour set on `ui::my_library::the_band_is_up`, the chip row on its own `ChipOwner` through `hero_chips::clear_if_stale`. Which leaves the leave a *page* leave in practice, with the collapse and the page's own teardown owning the rest. The full argument is the `HeroBackdrop` bullet above.
  - **A close doesn't run it, and that is the contract the morph forced.** Every fact the band paints — title, subtitle, artwork, blur quartet, badge, and through `HeroBackdrop` the tile fill and text tiers — is a ternary over the detail id at `my-library-view.slint`. Both halves used to clear on the frame the id did, so `close-detail` left the band spending its whole 400 ms collapse painting a fallback glyph over a reset gradient: an exit morph *from* a placeholder rather than from the banner it was collapsing. The fix is in two parts, and neither works alone. The sheet **latches which arm the banner paints** (`hero-album` / `-artist` / `-genre` / `-playlist`, seeded by their bindings and written only while some detail is open — so a cross-tab drill still moves them and a close does not, and `hero-*` is what the band's inputs read where the *body* router and the pill rows read the live `*-open`). **All four are written together, by one `latch-hero()` the four `changed *-open` handlers share, and that is not tidiness.** Each is written from nowhere else, so a handler moving only its own arm leaves the other three holding the last drill's answer — and the hero facts are ternaries tested in declaration order, so a stale `hero-album` outranks whatever opened after it for the rest of the page mount. The reachable shape is a *close or a tab-leave followed by a drill into a different tab*: on that frame no detail is open, so the guard correctly holds all four, and the next open then moved one. What painted was the previous album's title and tile over a playlist's body — and a tab leave releases the *images* but not `AlbumDetail.album`, so the wrong entity was named rather than merely blank. Pinned by `my_library_tests::the_hero_reads_a_latched_arm_where_the_body_reads_the_live_one`, which counts the writes inside `latch-hero` as well as checking each handler routes through it. And the teardown moves out of the four close handlers onto **`MyLibrary.hero-collapsed`**, fired by a `dur-spatial` `Timer` in the band — the `Dialog.closed()` shape, for the same reason it has one. The timer is armed and cancelled by the one edge that drives the morph, so a re-drill inside the window can't land the previous hero's teardown on the new one. **The backstop is the page's own teardown rather than the per-tab leave**, which now holds the hero instead of handing it back (see the `HeroBackdrop` bullet above): a nav away mid-morph kills the timer with the sheet, and only a seam carrying no tab predicate reaches the details left open on tabs that aren't mounted. `release_collapsed_hero` (`callbacks/my_library.rs`) asks **all three** image-bearing globals through the narrower **`release_hero_slots!`** — all three rather than the one that closed, because the band can't say which and doesn't need to — but hands each back only **on its own id**, because the band collapses for two reasons and only one of them closed anything: a tab switch out of a still-open detail collapses it too, and picking that tab again morphs the same banner straight back open. It clears the chip row and leaves the colour set alone, that being the page's to reset. Pinned by `my_library_tests::no_close_detail_hands_the_hero_back`, `hero_backdrop::tests::the_collapsed_teardown_hands_back_only_what_closed`, and the band's own deferred-teardown and cancel-edge pins.
- **Dialog-close releases global Image properties + scalar state — via exactly one handler.** `Dialog.closed()` fires once close-anim `t` returns to ~0, and there is **one** `on_closed` registration in the tree (`callbacks/playlists/dialog.rs`). It does both halves: `Dialog.invoke_closed_teardown()` (the Slint side — `kind`/`target-id`/`input-text*`/`mosaic-*`/`pending-track-ids`/the two picker row models/`title`/`message`/`cancel-label`/`destructive`; restore `confirm-label` to `"OK"`, don't clear to `""`), then `current_artwork` **and** `TagEditor.cover` reset to `Image::default()` (the two `image`-typed global properties, which have no Slint default literal) + `heap_trim::trim`. **The teardown is a Slint `public function`, not a callback body, and that is load-bearing:** a callback has a single handler slot, so a default `closed => { … }` body in `globals/dialog.slint` is installed at `InnerDialog::new()` and then silently **replaced** by the Rust `on_closed` (a plain `Callback::set_handler`). A `public function` has no slot to clobber. `CompositeScroll.reset()` (`globals/shell.slint`) is the second global to take this shape, for the same reason. Do **not** clear in `accepted`/`cancelled` — unmounts body mid-fade. Do **not** re-register `closed` from inside the handler (`Callback::call` `take()`s the handler and asserts). New dialog kind pinning an image extends the single `on_closed` — never adds a second.

## Popups, native dialogs, input

- **PopupWindow auto-dismiss on OS focus loss.** `melodia-ui/ui/components/focus-loss-watcher.slint::FocusLossWatcher` — one-shot component firing `close()` when local `Theme.window-focused` mirror transitions false. Mounted inside `if popup-is-open` so only the open popup has a live watcher; singletons gate on `PopupHighlight.id == "<discriminator>"`; per-row context menu gates on `PopupHighlight.row-ctx-id == row-data.id` (set on right-click, cleared in `winit_filter.rs` Release path). Slint 1.16 has no `closed` callback, but `pop.close()` is a safe no-op when hidden. `changed` MUST watch local mirror — Slint rejects path expressions on globals.
- **Native dialogs (rfd) — always through `ui::file_dialog::parented(&weak, title)`.** UI thread via `slint::spawn_local(Compat::new(...))`; the helper owns the `weak.upgrade()` + `.set_parent(&ui.window().window_handle())` half and the caller chains its own `add_filter` / `set_file_name` / `pick_*` / `save_file`. Requires `slint = { features = ["raw-window-handle-06"] }`. **Never build the dialog inline**, and the reason is that the bug is invisible here: without the parent it z-orders behind Melodia on Windows and macOS, while Linux's XDG portal parents OS-side regardless — so an unparented dialog looks right on the only platform anyone runs it on. Five call sites (Add Folder, playlist import / export, the tag editor's cover pick, the diagnostics bundle), held there by `ui::file_dialog::tests::every_native_dialog_is_built_by_the_shared_helper` — which **walks `src/` rather than naming them**, since the site that gets this wrong is the one nobody has written yet, and carries a caller floor so a caller that stops opening a dialog trips it too.
- **Keyboard shortcuts** — the root `FocusScope` is `ShortcutScope` (`melodia-ui/ui/layout/shortcut-scope.slint`), which owns every binding below plus the volume-commit debounce; it takes the whole main layout as its children. Grabs focus on `init`, and re-grabs via `shortcut-scope.grab-focus()` on every content-view switch — Slint doesn't hand focus back to an ancestor scope when the focused item is destroyed, so a view unmounting with focus inside it (a filter `SearchBar`) leaves shortcuts dead until the next click. Ten of the root's `changed` mirrors regrab it. Nine are one per branch selector of an `if` chain that mounts a view: `Nav.selected-index`, `MyLibrary.tab-idx` (which mounts one of nine bodies inside the page), `Nav.now-playing-open`, the four `*Detail.*-id`s and `mini-switch.render-active` for the content panel, plus `Dialog.kind` for the overlay's own chain (whose bodies die the same way — `closed-teardown()` clears `kind`). Same reason `CompositeScroll.reset()` needs its five, so a new always-mounted mirror that unmounts a *composite* view owes both. The tenth, `Queue.open`, is the exception that isn't about destruction at all: the sheet is permanent and mounts nothing, but its keys sit here and *nothing else moves focus onto it* — the bar button and the overflow entry are TouchArea clicks — so without the grab a filter `SearchBar` keeps the keyboard behind the sheet's backdrop and eats the `a`. Gates non-Esc on `!Dialog.open`. Typed keys in TextInputs never reach root. Bindings: Space play/pause; ←/→ seek ∓5s (Shift ∓30s, Ctrl prev/next); ↑/↓ vol ±5 (Ctrl ±1); 0–9 seek 0–90%; M mute; L favorite; N/P next/prev; S shuffle; R repeat; Q queue sheet (all three queue bindings mini-gated — the sheet doesn't exist in miniplayer mode, and arming `Queue.open` with no mounted mirror to fire `open-changed` remounts it rows-less); F Now Playing; F11 maximize; Esc Dialog cancel → queue sheet (clear selection, then close) → NP close; Ctrl+A queue select-all; Ctrl+B sidebar; Ctrl+, settings; Ctrl+N new playlist; OS media keys via souvlaki. **`ShortcutScope` is the only `FocusScope` in the tree, and the queue sheet is why that's worth stating.** Its Esc / Ctrl+A used to live in a nested `FocusScope { enabled: Queue.open }` inside `queue-sheet.slint`, but a `FocusScope` takes focus on **mouse press** (`i-slint-core/items/input_items.rs`), never on mount — so both keys were dead on a sheet opened with `Q` and only worked after a click on the sheet's blank area, and once the `Dialog.kind` mirror above started regrabbing they died again after any confirm dialog raised from the sheet. Both now sit at the root gated on the scope's `queue-sheet-up` (`Queue.open && !MiniPlayer.active` — the flag alone survives the miniplayer swap that unmounts the sheet), which also fixes the priority: Esc reaches the *dialog* first instead of the sheet's scope, and the `!Dialog.open` gate keeps Ctrl+A from firing behind a modal. A second scope would reintroduce all three problems — put new key handling here.
- **Animated view transitions** — Main-content branches mount via `ViewTransition`: enter-only fade + 32 px axis slide over `Theme.dur-spatial`. No exit anim — Slint `if` destroys outgoing instantly. Direction on `Nav.pending-enter-from: NavEnterFrom` (`{ below, right, left }`) — sidebar=`below`, drill-in=`right`, back=`left`. Write **synchronously on UI thread just before** flipping `if`; routed via `src/ui/nav_transition.rs`. `ViewTransition` flips `shown` via single-shot 1 ms Timer. Panel `clip: true` masks overshoot.
  - **A page with sub-views nests a second one, and it has to be disarmed at mount.** Favorites and Recently Played wrap each tab body in its own `ViewTransition` so a tab pick slides sideways — forward along the bar enters from the `right`, back from the `left`, which is the drill-in/back vocabulary reused for lateral movement. But the page's *own* enter is still playing on the frame its first tab body mounts, and a horizontal slide composed with the sidebar's fade-up reads as a diagonal. Hence `in property <bool> enabled` on `ViewTransition`: off, its `settled` guard is true from the first evaluation, so the three geometry bindings never transition and the `animate` blocks never engage. The host arms it in the tab bar's `selected` handler — the same place it sets the direction, and for the same ordering reason `nav_transition.rs` has (the bar has already written `selected-index`, but Slint re-evaluates the `if` at the next frame, so both writes land first). Starting `false` and arming on a real pick is what makes the page re-disarm for free, since it's destroyed and rebuilt on every entry; *arming* it from a mount `Timer` instead would race `ViewTransition`'s own (the `page-w` mirror's timer beside it is a different job and fine). The **direction** comes off `bar.previous-index`, so the host keeps no tab state and needs no mount seed — the page can be re-entered on any tab, and every other index in reach reads the tab just picked. It was a local `prev-tab` mirror seeded from the global, which is exactly the trap the bar's ordering sets: the seed was dirty by the time the handler read it, `i > prev-tab` was `i > i`, and every first switch after an entry slid in from the left. The handler's own write orphaned that binding, so picks two onward were right — which is what made it read as a one-off glitch rather than a seed bug.
    - **My Library nests the same thing and answers the *direction* question differently, because it is the one tabbed page with details.** Nine branches, five tab bodies and four detail bodies, and a body mounts three ways: a tab pick, a drill in, a back out. Bound to `band.tab-enter-from`, the two that aren't tab picks slide whichever way the last tab pick went — and a back out of a detail is exactly the case `nav_transition::mark` has already written `Nav.pending-enter-from = left` for. So **all nine branches read `Nav.pending-enter-from`** and the sheet writes the band's answer into it inside `tab-selected`, keeping one source of truth for a pick, a drill, a back and a Mouse-4/5 step. The band settles `tab-enter-from` before it emits, so that read is already the new one. `enabled: band.tab-anim-armed` still gates the five tab branches and deliberately does **not** gate the four detail ones — a drill-in is not the page's own entry and has nothing to compound with.

## Settings and nav wiring

- **Section-visibility hooks go through `SectionActiveGate`** (`melodia-ui/ui/components/section-active-gate.slint`), mounted in `app-window.slint` in nav-index order — **once per section, plus one more per tab for a section built out of tabs**. It owns the predicate — the section's index is selected *and* neither the full-screen Now Playing view nor the miniplayer is covering it — and fires `active-changed(bool)` into that section's Rust hook, which releases the section's cover caches on the way out and re-warms (or un-dirties) them on the way back in. Non-visual, `FilterThrottle`-style, so it costs no layout. **The gate has to be mounted on the always-alive `AppWindow` root, not inside the view**: the leaving transition is the edge that matters and a view cannot observe its own, since Slint destroys it instantly with no unmount callback. A new section adds one mount, not a tenth copy of the predicate; pass `mini-active: mini-switch.active` (the switch's live derivation, which leads the `MiniPlayer` global by a beat).
  - **A tab switch is a section switch, and the gate is where that becomes true rather than each view.** `tab-index` / `current-tab` are an optional sub-predicate, both defaulting `-1` so the predicate short-circuits and the four tabless mounts are untouched. My Library mounts five at `index: 3` with `tab-index: MyLibrary.tab-<x>; current-tab: MyLibrary.tab-idx`, so leaving a tab fires the departing view's existing `section-active-changed(false)` and entering one fires the arriving view's `true` — **every lifecycle hook then works unchanged**: cover release, model clear, `mark_dirty()` → re-fetch. Two things follow. The page needs **no `covers-generation` machinery** — the curated pages needed it because a tab pick had no fetch to hide behind, where here the entering tab's own fetch prewarms its first screenful before it writes rows — and background `library_changed` bumps stop rebuilding four hidden grids while one tab is up. **What the five genuinely cannot answer is the page's own leave** — only the *mounted* tab's fires, the other four having gone inactive at whichever tab pick came earlier — and that was harmless while a tab leave handed its hero back. It no longer does (below), so a detail left open on another tab is reachable from nowhere else. **The answer is not a sixth mount, and the reason is worth stating because a sixth mount is the obvious shape and compiles:** a gate fires on *transitions of its own predicate*, that predicate is already false while Now Playing covers the band, and `sidebar.slint` clears `now-playing-open` and writes the new index in **one** handler — so the leave that matters most goes false → false and delivers nothing. `MyLibrary.page-active-changed` therefore rides `app-window.slint`'s `changed watched-nav-idx`, beside `CompositeScroll.reset()` and the focus regrab, which are the other two "the mounted content view changed" concerns. Watching the index is also what makes "covered" and "left" different events for free, Now Playing and the miniplayer never moving it; the Rust hook re-reads it anyway, cheaply, so a second seam can't get it wrong. **A mirror fires on every nav change, though, where a gate fired only on its own predicate — so the hook owes a latch, and it is the half a later edit is likeliest to read as redundant.** A `changed` handler cannot ask which index it moved *from*, so an unlatched teardown runs on Search → Browse as readily as on a real page leave, and what it hands back there is the cover and blur pair `seed_detail_from_settings` wrote at boot **because** the page was hidden — the "leaves the page ready to paint" half of the publish gate two bullets up. One lateral nav before the first My Library visit and the band morphs open on `ArtworkImage`'s fallback glyph for a full `fetch_grid` + `refresh_detail` round trip, which is the flash the rest of this bullet exists to stop. The latch is a `Cell<bool>` on the closure seeded from `the_band_is_up`, which is sound for the `seed_tab` reason one bullet down: `install_views` hydrates the nav index before `wire_my_library` runs. It has to live in Rust rather than as a `prev-nav-idx` mirror beside `watched-nav-idx` — `Nav.selected-index` is declared `: 3` and the persisted index lands after `AppWindow::new()`, so a Slint seed is either a constant that fires one spurious teardown per boot or a binding that re-evaluates to the *new* index inside the handler and reports the leave backwards. Pinned by `ui::hero_backdrop::tests::the_page_leave_is_gated_on_the_nav_index_rather_than_on_the_gate`, whose two load-bearing assertions are the one refusing a `page-active-changed(active)` anywhere in the sheet — the spelling a `SectionActiveGate` re-home would take — and the one asking the handler to still latch. The cost is that a tab pick is a full re-query plus prewarm, identical to the sidebar switch it replaced but invited more often; the alternative — keeping the departing tab's models alive — is the Favorites shape and costs five tabs' row `Vec`s resident at once. A `0` default on either new property silently deactivates all nine sections, which `ui::tab_bar::tests::the_section_gate_ignores_its_tab_predicate_when_a_section_has_none` pins.
  - **The gate fires on transitions only, so each section's synchronous `section_active` shadow has to be seeded correctly on its own — and that is a boot-ordering constraint, not a `wire_*` detail.** Every `wire_*` seeds by reading `Nav.selected-index`, so `boot::ui_setup::install_views` writes the **persisted nav index before `wire_all`**, ahead of all nine — and `ui::my_library::seed_tab` beside it, for the same reason one step down: the five My Library seeds read `tab_is_mounted`, so a tab seeded after `wire_all` leaves all five answering for the global's declared `0` and costs one full-library Tracks query per launch. Pinned by `boot::ui_setup::tests::the_persisted_my_library_tab_is_seeded_before_any_view_is_wired`. It used to hydrate afterwards, and the cost is easy to under-read: `Nav.selected-index` is declared `: 3`, so *every* boot seeded `TracksUi` active and the section actually being restored inactive. **What decided whether a given gate ever corrected that is the tracker's baseline, not a dropped callback.** `ChangeTracker::init` evaluates inside `AppWindow::new()` and adopts the result **silently** — it assigns straight into the tracker's stored value and never calls the notify half, and `init_delayed` (the variant that would defer the first eval so it *can* notify) appears nowhere in the generated tree. So the boot reading never reaches Rust and becomes the baseline every later evaluation is compared against; a gate whose baseline already equals the value it settles on has no edge left to deliver. With `mini-switch.active` true on that pass (window width 0 until the geometry restore) every gate baselines `false`, and the asymmetry is the opposite of the intuitive one: **the restored section self-corrects** — its gate goes ∅→true once the window is sized — while **Tracks stays wrongly active all session**, seeded `true` against a baseline that was already `false`. That is not a cosmetic stale tier: `install_library_changed_refresher` then takes its ungated arm for a hidden view, which its own doc comment describes as re-fetching the whole library per song during plain listening. Seed from a hydrated global and none of it is load-bearing.
- **Nav state persistence keyed by view-id.** All in `views.json` (`ViewStateData`): `last_nav_index` mirrors `Nav.selected-index`; `last_detail_ids: HashMap<String, i64>` holds open detail per tab keyed by `view_id`. Setter `library::settings::set_last_detail_id` writes via `mutate_view_state`. Sidebar nav does NOT reset detail ids; only back button does. Adding detail = `view_id::*` const + open/close `set_last_detail_id` + seed fn. **A persisted view flag is an int/string/map, not a bool.** `ViewStateData` sat at clippy's `struct_excessive_bools` cap on three section-collapse flags until the Favorites strips became tabs and took two of them with it; `settings_tab` / `favorites_tab` / `recently_played_tab` / `my_library_tab` (`i32`, clamped on read by `ui::tab_bar::clamp_tab` against the page's Slint-declared `tab-count`) are the worked examples, and each sidesteps the cap by being an index rather than a booleans-per-section set. **`browse_view_mode` is the case where the rule bites hardest**, because it is the one genuinely binary flag on the struct — two presentations, list or cards — and a `bool` is what it would have been written as anywhere else. As an `i32` clamped against `Browse.view-mode-count` it costs nothing extra today and buys the third presentation for free; as a `bool` it would have put `ViewStateData` back on the cap *and* made the widening a migration. `artist_albums_collapsed` is the one survivor. Dropping a field is safe on shipped installs — serde ignores unknown keys, so an old `views.json` upgrades in place and lands on the first tab (`test_view_state_ignores_the_retired_collapse_flags`).
- **Anything on the Settings page that has to fit a width reads `SettingsPage`, and never measures.** `settings-view.slint` publishes two facts imperatively — `page-w` (the panel width it already mirrors; a live `root.width` read feeding a child's size re-enters layout) and `body-cols` — and the global derives `body-w` / `card-w` / `row-content-w` from them. Every card spans a full body column, so those are exact rather than approximate, and a control four levels down can size itself with no width mirror, no mount `Timer` and no `parent` reach-around. **`row-content-w` is the one to want**: the width a `SettingRowStacked` leaves its content block, which is what `ChipGroup` and `ColorDotGrid` default their `avail-width` to. Override the property at a call site that isn't a full-width card row; don't recompute the number.
  - **Wrapping a strip of items: `SettingsPage.chunk-indices(count, per-row) -> [[int]]`** (`src/ui/settings_page.rs::chunk_indices`), then `for row in …` / `for idx in row`. Slint 1.16 has no `Flow` and can't build a nested array, so the split comes from Rust and the strip iterates two real arrays. Reach for this shape rather than re-deriving one: the two obvious pure-Slint approaches are both dead ends, since an inline `for … : if …` is rejected outright and a `Rectangle` wrapper around a filtered-out item still claims its parent layout's spacing. `ChipGroup` was a hand-unrolled 4+4 split capped at eight chips for exactly that reason.
  - **How many fit is measured, not estimated — and the arithmetic around that measurement is shared.** `SettingsPage.wrap-per-row(avail, item-w, gap)` and `wrap-height(count, per-row, cell-h, gap)` sit beside `chunk-indices` because `ChipGroup` and `ColorDotGrid` derived both identically; what differs is only where the item width comes from. `ChipGroup` mounts a hidden `visible: false` ruler of one real `Chip` per option and takes `measure.preferred-width` — a `VerticalLayout` reports the max of its children's widths, so that *is* the widest chip. Same idiom, and the same reason, as `TabBar`'s ruler below: same component measured and drawn, so the two can't drift, and it follows the running locale for free. Sizing every row off the widest is deliberately conservative — the chips keep their natural widths, so a row is never full but can never overflow, and no per-item measurement has to escape the repeater. `min-width: 0px` on the root is load-bearing: without it the ruler's width leaks back out as a floor on the card, which is the thing the wrap exists to remove. A fixed-size strip (`ColorDotGrid`, 32 px dots) needs no ruler — the count is arithmetic.
- **Tab bars via `TabBar`** (`melodia-ui/ui/components/tab-bar.slint`), mounted **once**, by `components/hero/tab-search-header.slint`'s `TabSearchHeader` — the row carrying the bar and the filter box together, which the Settings page and both shared hero bands (`MosaicTabHero` for Favorites and Recently Played, `LibraryTabBand` for My Library) each spelled out for themselves until it became a component. Reach for the *row*, not the bar: a page wanting tabs beside a filter wants all five of the fixes in it, and the bar alone is where three copies of them came from. It takes the whole row's width as `avail-w` (the host owning its own mirror, since a live `root.width` read feeding a child re-enters layout) plus an optional `lead-w` + `@children` for a leading slot — My Library's morphing back button is the only one — and publishes `row-floor` (seed your mirror off it), `row-h`, `search-w`, `tab-enter-from` / `tab-anim-armed` and the six `tip-*` anchors. **`tip-x` and `tip-y` both carry the bar's own `absolute-position` offset inside the row**, and that is the half a host cannot supply — it only knows its own `header ↔ root` delta. Dropped from `tip-x`, the pill lands a whole `lead-w` left of the tab it names, on the one mount that has a leading slot and only while that slot is open; the two mounts without one put the bar at `x == 0`, so four of the six places you would look agree with the bug. `ui::tab_search_header_tests` pins both axes. Pinned by `ui::tab_search_header_tests`, which also holds the three hosts to mounting it rather than regrowing a bar of their own. Data-agnostic — parallel `labels`/`icons` arrays, `avail-width`, `selected-index`, `selected(int)`, the same shape as `ChipGroup`/`Dropdown`/`ColorDotGrid`. **It also publishes `previous-index`, and that exists because a cell writes `selected-index` before it emits `selected`** — it has to, since the `<=>` on that property is what carries the pick out. So a host's handler runs with `selected-index`, and anything two-way bound to it, already reading the tab just picked; the outgoing one is recoverable nowhere else. Favorites derives its slide direction from it. The same write-before-emit ordering is why the Rust side needs `apply_filtered_grids_now` (root `CLAUDE.md`) — the entering tab's `if` is already true when `tab-changed` lands — so a host that wants the *old* index should reach for `previous-index` rather than mirroring `selected-index` and seeding the mirror at mount, which is the shape this replaced. **Material 3 tabs: a sliding underline, and no fill on the selected tab** — accent label, accent icon at `filled: true`, and a 3 px accent pill sitting in a gap in the 1 px divider carry it three ways. Hover keeps a state layer at `radius-md` rather than the square full-bleed rectangle M3 specifies, matching the settings rows below it. The cell fills its own bounds and the **row** gives the clearance — one `padding-bottom: pad-sm` on the tab `HorizontalLayout` reserves the divider/pill band, so a rounded fill floats above the line instead of resting on it, and the content re-centres in what's left rather than the bar getting taller. That's still the deliberate split from the ChipGroups *inside* the settings rows, which do fill: the bar navigates, the chips configure, and one page showing both needs them to read as different things. **The label weight is constant 500 across both states**, which is load-bearing rather than cosmetic — see the equal-width cells below. **The bar sits in the page header where the title used to, flush left, sharing that row with the search bar** — so the divider and underline span the bar rather than the page. On Settings the title was deleted rather than displaced: no other page's heading sat directly over five tabs reading Library / Playback / Interface / Services / About, which name the page better than the word above them did, and the sidebar item and window title still carry it. Reclaiming the row is what puts the bar at the top of the page instead of pushing the body down. Favorites keeps its title, because the tabs there name *sub-views* rather than the page.
  - **Every brush it paints with is a defaulted `in property`** — `label-color`, `active-color`, `hover-fill`, `divider-color` — and that is what lets it sit on a hero. Settings takes the defaults (`Theme.text` / `accent` / `surface0` / `surface1`) and is unchanged; the two hero bands hand over `HeroBackdrop` tiers for **all four**, per the "anything painting on a hero blur reads `HeroBackdrop`, never a `Theme.*` brush" rule above. **Neither band hands a tier over raw — both go through four locally eased `dur-med` mirrors** (`hero-label` / `hero-active` / `hero-hover` / `hero-divider`), because the bar itself may not ease a brush and the solve lands late either way. `MosaicTabHero` passed them straight through until it didn't, and it is the band that   - **The Rust half is `src/ui/tab_bar.rs`**, and it is one function: `clamp_tab(tab, tab_count)`. All four hosts persist their active tab (`views.json`'s `settings_tab` / `favorites_tab` / `recently_played_tab` / `my_library_tab`) and all clamp on *read* against the Slint-declared `tab-count` — the bar can only ever produce a valid index, but a file left by a build with more tabs would select a branch that mounts nothing. The component's two source-level invariants (the written-not-bound `compact-t`, the root's `clip`) are pinned there too, since neither host owns the file any more.
  - **The header row is three instances, and only one of them is still hand-written.** It is five things: a `page-w` mirror written from `changed width`, a 1 ms mount `Timer` re-running that mirror, a seed at the row's own floor (`2*pad-lg + bar.compact-w + 2*pad-md + search-w-max`), the `search-w`/`avail-width` budget reserved against the bar's published `compact-w` and the input's published `min-w`, and a top-layer tooltip frame declared after the scroll chrome. Every one is a paid-for fix documented below or in `slint-pitfalls.md`, which is exactly why a *third* hand-written copy was the wrong answer when Recently Played became tabbed: the two mosaic pages share **`components/hero/mosaic-tab-hero.slint`**'s `MosaicTabHero`, My Library has **`components/hero/library-tab-band.slint`**'s `LibraryTabBand`, and Settings keeps its own. The forwarding tax that made a wrapper a bad trade at two call sites is real and paid — some twenty `in`/`out` properties and three callbacks — and what buys it back is that the band is the *whole* banner rather than just the row: the blur backdrop, the mosaic tile, the title, the chip strip and the bar all move with it, leaving each page a mount sheet. **Settings stays out**, and not for want of a third caller: it shares only the arithmetic — no hero, no mosaic, no title, and its bar takes the `Theme.*` defaults where a hero's takes `HeroBackdrop` tiers. **The two bands are siblings and not one parameterised component** for the reason one level up: they differ in the mosaic-square-versus-artwork-tile and in a fixed height versus a morph, which Slint has no way to abstract over — so the five fixes above are *ported verbatim*, and `ui::library_tab_band_tests` exists to hold a copy to a contract a copy is exactly how you lose. **Two things can't move into the band, and stay at each host.** The per-tab `ActionPill` rows reach it as `@children`, placed after the meta block's trailing spacer so they sit on the band's floor — which is also the slack `HERO_MAX_ROWS` is measured against. And the tooltip frame has to be declared after the scroll body, Slint painting in declaration order, so the band publishes `tip-x` / `tip-y` / `tip-w` / `tip-h` / `tip-label` / `tip-visible` (derived from the hovered *index*, so a tab moving under a parked pointer keeps its anchor) and each host spells five lines. Pinned by `ui::mosaic_tab_hero_tests` — the seed, the mount `Timer`, the budget's two published floors, the four `HeroBackdrop` brushes, the disarmed slide, and that the tooltip is published rather than drawn — with `ui::settings_page::tests` holding Settings' copy of the first two.
  - **`LibraryTabBand` is the band that *morphs*, and everything unusual about it comes from that.** Idle it is a flat `Theme.base` pane carrying the tab bar, the shared filter box and the mounted tab's count (≈132 px); with a detail open it grows into that entity's hero — blur backdrop, artwork tile, title, subtitle, chips — with the tabs still in it and a back button to their left, at `MosaicTabHero`'s `hero-height` exactly (232 px, the same formula, so the two bands agree on what a hero is). One animated float `hero-t` drives the height, the backdrop reveal, the back slot, the palette and the count line's exit. Six things to know before touching it, each paid for once:
    - **The height is a `min-height` / `preferred-height` / `max-height` split with `clip: true` on the root, never a bound `height`** — the animated-root-dimension pitfall, one axis over from `tab-bar.slint`'s. The clip is what the split obliges: it buys the freedom to be drawn shorter than asked, and the hero content would otherwise paint out of the compact band into the body.
    - **`hero-t` is *written* from `changed detail-open` and only seeded by its binding**, so a page entered with a detail already open lands at hero height instead of growing into it, and a detail id moving underneath can't re-base the curve.
    - **What may hang off an `if` is decided by change trackers, not by taste.** Everything tracker-free rides one `hero-shown: detail-open || hero-t > 0` — both ends of that predicate were bugs, a frame early on the way in and 400 ms late on the way out. The chip strip **cannot** join them: it carries `MetaChipStrip`'s `changed watched-w` over a layout property that a morph re-dirties every frame, so dropping its branch panics. It stays mounted for the life of the band and fades by brush alpha instead. **What each half fades *on* is a second question, and only the artwork tile still answers `opacity`** — an image fills its box, where a text run's ink does not, and an `Opacity` layer is sized to child *geometry*. The title block sat on `opacity` for a while, exempted on cost because its layer was transient, and cropped every Arabic mark that leaves the line box for the whole 400 ms — the hamza above an alif, the dots under a final ya — handing them back on the settling frame, which reads as a morph that didn't finish. It takes brush alpha now, like the idle pane and the count line beside it. Full argument for both in `slint-pitfalls.md`.
    - **The palette crosses through `states`/`transitions` with eased `HeroBackdrop` mirrors beside it**, because the hero half of each pair rides the artwork decode and lands late; see the `TabBar` brushes above.
    - **The count line is anchored to the *compact* floor and the pill slot to the animated one**, which is the whole difference between them: a detail's pills belong on whichever floor is current, so they follow the height, while the idle count belongs where it already sits — riding the height dragged it off the page and shoved it back. It leaves sideways on `count-slide` instead, its alpha a *bias* off `hero-t` rather than the plain complement so it doesn't read through the artwork tile fading in behind it.
    - **The back disc scales on both dimensions with `hero-t`**, so every frame is a uniform scale of the settled row and there is nothing for the slot's clip to cut; its alpha is a doubled bias for the same reason the count's is biased — it is the only piece of the hero whose *size* also rides the morph, so a plain alpha would have made its presence go as `hero-t` squared and read as a pop at the end.
  - **The cells are equal width, sized to the widest tab, and that is what makes the underline arithmetic** (`ind-x: tab-w * anim-index`). A `for` loop exposes no per-tab element to read a position off, so a content-sized row would have to snapshot each tab's geometry on selection and go stale on every resize. It costs a little width (5 × widest > sum of naturals) and buys a sliding indicator with no bookkeeping. It is also why the selected label can't be heavier: the cell was measured against one weight.
  - **What eases is two sources; every geometry derives from them unanimated.** `anim-index: root.selected-index` (`dur-med`, `ease-in-out`) owns *a tab was picked*; `compact-t: root.compact ? 1.0 : 0.0` (350 ms, `cubic-bezier(0.2, 0, 0, 1)` — M3 emphasized-decelerate) owns *the bar changed shape*. That duration is inlined rather than taking `dur-spatial`: the flip fires under the user's hand on a resize drag, where a 400 ms tail reads as the bar lagging the window instead of as a gesture. Those two `animate` blocks are the only ones in the file outside the cell's own three floats — **and floats are all a cell may ease.** Its `icon-color` used to ease and couldn't: a host crossing its palette re-dirties that binding every frame, so the glyph sat still until the source settled and then caught up in one rush. The hover fill was exempted next, on the grounds that its ternary reads the host's brush only on the hovered arm — which is exactly the arm live when you hover a tab and click it, so the picked cell kept the theme's grey for the whole morph. Both are floats now (`hover-t` on `dur-fast`, `sel-t` on the underline's own `dur-med`/`ease-in-out`) with the brushes tracking their sources unanimated; `sel-t` is what crosses the selected label and glyph *with* the sliding pill instead of stepping ahead of it, over two stacked layers, since `mix()` has no brush overload. Full argument, including why the bottom layer stays at full alpha, in `slint-pitfalls.md`. **`compact-t` is seeded by that binding and owned by `changed compact`, which writes it** — the binding is live only until the first flip. That is load-bearing at both ends: writing it swaps the animated binding for an animation of its own (`set_animated_value` → `set_binding`), which is what stops a resize drag restarting the curve on every event, and keeping the binding as the seed is what leaves mount alone, since it is still live for the first evaluation and that one lands in `NotAnimating` and takes the value straight through. A constant seed plus a mount `Timer` would morph on every entry into Settings at a compact width. The latch below earns its keep twice over as a result — each `changed compact` is now a real restart, so a threshold that flapped would be visible rather than merely wasteful. **The ease is gated on an `eased` flag a 100 ms mount `Timer` arms**, because the *first* resolution isn't a change — it's the bar learning how much room it has. Since the host seeds its width at the row's floor (below), every mount settles compact and a roomy panel corrects to expanded a frame later; easing that would play an unasked-for morph on every entry into Settings, so it snaps at `0ms` instead. 100 ms rather than the tree's usual 1 ms mount seed is the point — this has to *outlast* the host's first `changed width`, not race it, and no hand crosses the threshold that fast. It resets for free, since the page is rebuilt on every entry. `tab-w` interpolates `natural-tab-w → compact-tab-w` off the second, and `ind-x`, the pill, both divider segments, the bar's own `preferred-width` and the tooltip rect the host builds all fall out of the pair with no `animate` of their own. **They have to be two.** A single `animate` on `ind-x` or the pill's `width` conflates the two events, because both read `tab-w`, and the compact flip then reads as the pill flying in from the right on the way down and from the left on the way back up — its two edges travel different distances. That artifact is the pill *chasing an instant resize*: cell `i`'s left edge is `i * tab-w` and the pill's is `anim-index * tab-w`, so once `tab-w` itself eases, the pill sits under its tab in every frame of the morph rather than only at the ends. (This is why the file used to leave the resize instant and only ease the index — correct about the fix it rejected, wrong about the conclusion.) The divider is two segments cut either side of the pill (`width: ind-x` / `x: ind-x + tab-w`) rather than a line running under it, and they read `ind-x` directly for the same reason — a segment animated on its own would lag the pill by a frame.
  - **The bar sizes itself with `min-width`/`preferred-width`/`max-width`, never a bound `width` — an eased width on a component root moves the whole window's minimum.** Slint reports a root's bound `width` as *both* `min` and `max` (and rejects a `min-width` beside it outright), so binding `width: labels.length * tab-w` puts the bar's layout floor on the animated `tab-w`. That floor climbs the header row into the page and out to the window itself, so the window's own minimum width eases along with the morph: dragging the edge inward chases a wall that is still moving, and it **stutters**. Worse, the bar was then routinely the constraint stopping the window from reaching the very width its own threshold was waiting for, so whether the flip tripped at all came down to whether the title and search row happened to be wider — which is a locale-dependent coin flip, and reads as the responsive switch firing late or not at all. Splitting the three constraints fixes both: `min` is the constant `labels.length * compact-tab-w`, `preferred` tracks the animated cells so a centring host draws it exactly as the bound width did, and `max` keeps the upper half of what that meant. **Any component root whose `width` becomes animated owes this same split** — check `layout_info`'s Horizontal arm in the generated `app-window.rs` if unsure; `min` reading back the root's `width` property is the tell. **It also owes a clip, because the split buys the window's freedom by letting the element be drawn narrower than it asked for.** On the shrink leg `compact` flips the instant the threshold is crossed but `tab-w` takes 350 ms to follow, so `preferred` is still five natural cells while the row can no longer afford them; the layout squeezes the bar toward its `min` floor and the cells — bound widths, hence incompressible — paint past the right edge and under the search input. `clip: true` on the root contains it. Rectangular is the whole point: this root has no border and no radius, so it lowers to a scissor rather than the offscreen layer a *rounded* clip over text would cost.
  - **Sharing the header row means the two widths are budgeted, not independent.** `avail-width` is no longer the whole page: it's `content-w` (page less its padding — one property, shared with the body's own column-count decision) less the two 12 px gaps less whatever the input is taking, so the tabs give up their labels far earlier than they did centred on their own row. Going the other way, `SearchBar`'s slot never stretches past `input-width` (`preferred` and `max` are the same number, so focus-scaling happens inside the slot and never shifts its neighbours), which makes it the page's job to size it — it's driven from `clamp(content-w - bar.compact-w - 2 * pad-md, search.min-w, 220px)`. It does *compress*, to that same floor, which is why the budget below can be a sum rather than a hard reservation. **The filter yields before the tabs do**: tabs are navigation, search only refines what a tab already shows. Both ends of that clamp read a published floor — the tabs' `compact-w`, the input's `min-w` — rather than a restated `5 × 48px` or `140px`, and that is what keeps each from drifting from the component it budgets for, and it makes the row's minimum a sum the page can actually check — see the budget spelled out at `search-w-min`, which is sized against the narrowest panel Settings can be asked to draw in (the 550 px miniplayer cutover, less the sidebar's own floor).
  - **The threshold is latched, not bare.** A slow resize drag delivers a stream of one-pixel widths and a hand jitters over the last of them, so `avail-width < expand-w` flips on every one that straddles the line. Instant, that was invisible; eased, the bar hunts. `compact` compares against `expand-w + (latched ? hysteresis : 0px)` with a 24 px band, and `changed compact => { latched = compact; }` is the only state — the threshold itself is re-derived from `expand-w` every evaluation, so a locale switch still moves it. It converges in one step in both directions and needs no seed `Timer`: `latched` starts `false`, which is the honest reading at mount, and the first real transition corrects it.
  - **The label collapses onto its icon rather than unmounting.** `SettingsTab` takes `compact-t` as a float, not `compact` as a bool, and derives `open: 1.0 - compact-t`: the row's padding and spacing scale with `open`, so the `alignment: center` layout closes to just the icon and the icon glides to the cell's centre with no positioning arithmetic. The label lives in an always-mounted slot whose `width: label-w * open` — an `if !compact:` is what made the flip a pop. Three details are load-bearing: the slot's `clip` is **rectangular and borderless** (a scissor; a rounded one would render the text to an offscreen layer and upscale it on HiDPI), the label's fade is `label-color.with-alpha(…)` rather than `opacity` on the element (`opacity` costs a layer, and there are five cells), and the alpha is a *bias* off the same source — `clamp(1 - compact-t * 2, 0, 1)`, gone by the time the slot is half closed, so the clip never shows a half-eaten word. A second `animate` on the alpha would phase-lag it. `label-w` is `lbl.preferred-width`, read straight off the Text the cell draws: the generated binding is `layout_info(lbl, Horizontal, -1, …).preferred`, which never reads back the width it's handed, so the slot sizing itself from it is a derivation and not a cycle — the same thing that makes the ruler below safe. `cubic-bezier(0.2, 0, 0, 1)` keeps both y control points inside `[0, 1]`, so `compact-t` can't overshoot and no derived width goes negative; a back-out curve would need `clamp` on `open`.
  - **`compact` is measured, not thresholded.** A hidden `measure := VerticalLayout { visible: false; … }` mounts one **real** `SettingsTab` per label — the same component the bar draws, so the measured shape and the drawn shape cannot drift — and `measure.preferred-width` is the widest expanded cell. `compact: avail-width < labels.length * that`. The labels are translated, so the width that matters is the running locale's; the predecessor was a hand-derived `page-w < 780px` literal whose own comment ended "re-check it when adding a locale", and that obligation is now gone. **`compact` stays an instant bool on purpose** — it is the *decision*, and `compact-t` is that decision rendered over time. That split alone does **not** make easing the flip safe while `avail-width` changes continuously under a resize drag, and the claim that it did was wrong for a subtle reason worth keeping: Slint restarts an animated *binding* on dependency **dirtiness**, never comparing values, so it is irrelevant that the bool only ever sees a toggle — `compact` reads `avail-width`, the drag rewrites it on every pointer motion, and the 350 ms curve was torn down and restarted every few milliseconds. The gate is that `compact-t` is **written** from `changed compact` rather than left to its binding; see the sources bullet above and the pitfalls entry. The *threshold* can't chase the flip either — the ruler is always expanded (the drawn cells pass `compact-t`, the ruler's pass `0.0`), so `natural-tab-w` doesn't move when `compact` flips, nor while the flip is playing out. That is a different guarantee from not flapping under a jittering drag, which is the latch's job — see below. **The decision had to move into the bar**: a component may read `preferred-width` off its own descendant but not off a child component's internals (`menu-surface.slint`, `overflow-menu.slint` state the rule), so the host can only hand over `avail-width` and read the verdict back. It still hands over a **mirrored** width (`changed width => { self.page-w = self.width; }`, the `now-playing-bar.slint` `bar-w` idiom) — a live `root.width` read feeding a child's size re-enters layout — and it's the **content panel** less its own padding, not the window. **The mirror costs a frame, so what `page-w` is seeded to is a real decision, and it has to be the header row's own floor rather than a plausible page width.** The failure is asymmetric: seeded wide, the bar believes it can afford five full-width tabs and draws them into a panel that can't seat them, and under `alignment: start` they overflow the row. The bar's root now carries `clip: true`, so that overflow is cut off mid-cell instead of painting under the search bar — but a bar drawing five cells into a panel that seats two is wrong either way, and the seed is what stops it. Seeded at the floor it draws the icons it would have drawn anyway and widens once. A **miniplayer → full swap remounts the page at a panel far narrower than any plausible guess**, which is the reliable way to see the wide one — a literal `900px` sat there and looked harmless until exactly that. The floor is spelled `2 * pad-lg + bar.compact-w + 2 * pad-md + search-w-max`, the narrowest page that still seats the bar at `compact-w` *and* the input at `search-w-max`, so at the widths Settings is normally opened at neither pops a frame later; `ui::settings_page::tests::the_page_width_seed_is_the_rows_floor` pins that it stays derived. **A seed obliges a mount `Timer`**: `changed` doesn't fire when the first layout settles directly on the final value, and a window opened at its final size is exactly that — so without the 1 ms single-shot beside it the seed is never corrected and a roomy window still draws icon-only tabs until something resizes it. It only looked right coming out of the miniplayer, where the floor's answer happens to be the correct one.
  - `visible: false` is the right hiding mechanism here and worth knowing why: it lowers (`i-slint-compiler/passes/visible.rs`) to an injected `Clip` parent with `clip: !visible`, and that pass runs **after** `default_geometry`, so the injected element gets no geometry bindings and sits at 0×0. Nothing paints, `Clip::input_event_filter_before_children` intercepts anything outside its empty rect so the five hidden `TouchArea`s are unreachable, and the layout info the ruler exists for is still computed — the "`visible: false` doesn't remove from layout" pitfall read the useful way round. The generated `measure_…_layoutinfo_h` is a `box_layout_info_ortho` over the repeater with a `None` cross-axis constraint, i.e. it never reads the assigned width, which is what keeps `measure.width ← bar.width ← measure.preferred-width` from being a cycle.
  - **The compact tooltip is not on the tab**: the bar publishes `hovered-idx` (-1 for none) and `hovered-label`, fed by a per-tab `hover-changed(bool)` off a local `has-hover` mirror, and `settings-view.slint` hangs one `Tooltip { side: TooltipSide.below }` off a frame declared **after** both `OverlayScrollbar`s. Anchored on the tab it would sit inside the page header, which Slint paints *before* the scroll body, so the first section card covers it — the same fix, and the same frame-tracks-the-host idiom, as the `header-tip` My Library's mount sheet hangs off its Playlists pill row. Equal-width cells let the host derive the rect from the index (`bar.absolute-position.x - root.absolute-position.x + bar.tab-w * bar.hovered-idx`), so unlike the snapshot this replaced, a tab that moves under a parked pointer (Ctrl+B, F11) keeps its tooltip anchored to it — and since `tab-w` eases, that frame morphs with the cell for free. The gate stays on the instant `compact` rather than on `compact-t`: `Tooltip` owns a 500 ms reveal delay, longer than the 400 ms morph, so it can't surface while the label is still readable. Only the tab that owns the hover may retract it — keyed on its **index**, since a data-agnostic bar can be handed two tabs with one label — else a leave arriving after the neighbour's enter blanks a live one. Tab switches reset `sv.viewport-y` imperatively from two local `changed` mirrors — a short tab under a parked offset otherwise paints blank.
- **Audio installers seed from `ui::settings_bind::read_or_default(state, "…")`.** `install_{equalizer,replaygain,visualizer}` each opened with the same `match settings::read_settings(…)`, spelling its own defaults out again in the error arm — a second copy of the `Default` impl, and a second place for it to drift. The helper falls back to `SettingsData::default()` and logs, so the seed is derived one way whether the file loaded or not. Its sibling `toggle_binding` still owns the apply-then-persist shape. **Not every installer wants it:** `playback_settings` / `file_watching` / `updater_settings` use `if let Ok(s)` deliberately, leaving the **Slint-declared** defaults in place on a read failure rather than re-deriving them in Rust — converting those would change their fallback, not de-duplicate it.
