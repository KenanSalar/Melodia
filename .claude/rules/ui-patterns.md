# UI patterns — the shared components and what already exists

What to reach for instead of building a second one, and the two teardown paths that keep
the UI from pinning GPU buffers. This is the "reuse this" file; the things that *build,
look right, and are still wrong* are `.claude/rules/slint-pitfalls.md`, which loads on the
same globs.

A rule rather than a `CLAUDE.md` beside the code, for the reason the root file gives: UI
features cut across two trees (`.slint` under `melodia-ui/ui/`, Rust under `src/ui/`), so a
per-directory file would reach one and silently miss the other.

## Shared components

- **Tooltips via `Tooltip`** (`melodia-ui/ui/components/tooltip.slint`) — a plain absolutely-positioned pill, not a `PopupWindow`, so it captures no input and the host keeps its hover. Owns the 500 ms reveal delay and the fade; `side: TooltipSide.{above,below,right}` picks which edge it clears, and it takes `host-width`/`host-height` explicitly because a component root can't reach `parent`. **Two mount shapes.** In-tree (`IconButton`, `PillButton`, the traffic lights, the swatch dots) is the default and works wherever nothing clips or overpaints the host. **Top-layer** is for hosts whose tooltip lands somewhere Slint paints later: a frame `Rectangle` declared after the occluder, tracking the host's rect via `absolute-position` deltas, with the pill inside it. Three of those — `playlists-view.slint`'s `header-tip`, `settings-view.slint`'s `tab-tip`, and the collapsed sidebar rail's `sidebar-tip` in `app-window.slint`.
  - **The rail's tooltip is the one that crosses a component boundary, and that's what makes its channel a global.** It mounts in `app-window.slint` after the whole `VerticalLayout` — the `Sidebar` is the content row's *first* child, so anything it painted past its own right edge would land under the content panel, and `nav-scroll` clips it besides. The hovered row publishes itself on `Nav` (`sidebar-tip-idx` / `-label` / `-y` / `-h`, with `sidebar-collapse-tip-idx` as the Collapse toggle's key, since it sits in the rail but owns no nav index): the rail's rows are ten hand-written mounts, so routing hover up through `Sidebar` as an `out property` would put a forwarding line on each. Nine of the ten reuse the row's own `@tr` label for free; the toggle is the exception and reads `@tr("Expand")`, because the tooltip only ever shows on a collapsed rail and its row label says the opposite. The **x** is the one thing not on the global — it comes off `sidebar.width` live, so the frame rides the collapse animation, and the 500 ms reveal outlasts that animation so the pill can't surface while the labels are still readable. Same retract rule as the tab bar: keyed on the index, so a leave arriving after the next row's enter can't blank a live tooltip. **The gaps are what the tab bar doesn't have, and they need a hold.** Rail rows sit 4 px apart with a `Divider` between some pairs, so a pointer travelling down the rail is over nothing for a frame or two; retracting on that restarts the 500 ms reveal on every row change and the pill flashes the new label, fades out and comes back. The frame keeps a `held` bool that a row's enter sets and a 150 ms `Timer` clears only once nothing has taken the hover, and feeds *that* to `hovered` — the label and the frame's rect are untouched on retract, so the held pill sits still and swaps to the next name the moment that row takes over. The tab bar's edge-to-edge cells never drop hover in the first place, which is why it needs none of this.
- **Popup chrome via `PopupSurface`** — every `PopupWindow` body wraps `melodia-ui/ui/components/popup-surface.slint` (Theme.crust fill, 1 px Theme.surface2 border, Theme.radius-md, no entry anim). `pill: true` for vertical-pill.
- **Pill buttons via `PillButton`** (`melodia-ui/ui/components/action-pill.slint`) — 32 px outer / 28 px chrome, `Theme.surface1` hover. `danger: true` keeps that same chrome and only tints the icon **and** label to `Theme.danger` on hover — no permanent red fill, since Tauri's filled-red read as over-prominent for inline action rows. (The filled treatment is `SectionButton`'s, and it's the one that hover-lightens with `Theme.danger.brighter(10%)`; the two are not one pattern.) Compose inside `ActionPill` with `PillLabel`/`PillDivider`. **Sort-row pills** carry `reserve-sort-slot: true` + `sort-direction` — trailing 16 px `arrow_drop_*` slot. Never concatenate Unicode `↑`/`↓` into the label. `IconButton` for round controls *outside* chips.
- **Reusable grid + detail components.** Grids compose `EntityCard` in virtualized chunked-row `ListView` — Rust chunks flat list into `AlbumGridRow` of N; `GridColumnsSync` computes N from width, fires `columns-changed` for no-DB rebuild. Detail views compose `DetailHeader` (full-bleed dual-slot hero-blur backdrop + solved gradient floor + scrim, left artwork, floating back button, `@children`); callers supply an action pill.
- **Detail-page TrackList inset.** Album/Artist Detail wrap `TrackList` in `HorizontalLayout { padding-left/right: Theme.pad-lg }` to match `tracks-view.slint` / `browse-view.slint`. Detail root VL can't — `DetailHeader` is full-bleed for hero blur. Overlay scrollbars at `parent.width - self.width` (root-relative).
- **`play-row` replaces the queue with the view; there is no single-track play path, and no Play-All pill either.** Every row activation resolves the view's *displayed* ids and hands them to `library::playback::player_play_tracks(ids, start)`. Eight headers used to carry a **Play All** pill making that same call pinned to `Some(0)` — i.e. exactly what activating the first row does — so it was deleted along with `Browse.has-playable-files`, the flag that gated Browse's copy. Don't reintroduce it; the pill that remains — in six of those eight, Browse and Tracks never having had one — is **Shuffle**, which earns its place by flipping shuffle on, something no row activation does. All six route through the shared `ui::callbacks::spawn_play_then_shuffle`, which plays the list from a **random** slot and then calls `queue_set_shuffle(state, true)`. Random because the shuffle anchors the current track at the front, so a head start would open every press on the same song. And `queue_set_shuffle` rather than a read-then-toggle pair: the pill means "on", so a toggle racing the transport's shuffle button would turn it off, which is the TOCTOU that function exists to close. The start slot comes from the shared `ui::callbacks::play_row_start(&ids, id, idx)`, which trusts the index Slint passes when it lines up and otherwise falls back to a lookup by id (Browse's disk-only rows sit in the displayed list but not in `current_in_library_ids`, so its two index spaces differ). A new list view wires `play-row` to its own `*_track_ids()` helper — Search is the sole exception, reading `Search.tracks` through `model_track_ids` because its visible set is sorted and `COMPACT_TRACK_LIMIT`-truncated at render with no Rust-side cache. The Most Played strips have no row index (they're cards) and resolve the start by id against the strip; both strips are **filter-aware**, so `most_played_track_ids` walks the cache through `detail_filter::most_played_matches` — the same predicate `apply_filtered_strips` builds the model with, so the strip and the queue it loads can't disagree about what's on screen. `player_play_tracks` then re-resolves that slot by **track id** against what the DB actually returned (`resolve_start_slot`), since the fetch drops ids that no longer exist and every slot past the gap would otherwise shift. `player_play_tracks` re-shuffles anchored to the picked track when `shuffle_enabled`, so the transport's shuffle button can't stay lit over a queue playing in display order. Appending without wiping is the *context menu's* job (`queue_play_next_many` / `queue_add_tracks`) — don't reintroduce a play-one-track entry point.
- **Selectable-picker dialogs share one toolkit** (`melodia-ui/ui/components/dialog/selectable-picker.slint`: `SelectIndicator` + `SelectableRow` + `SelectAllHeader` + `PickerListCard`). Both the **Export** picker (`kind == "export-playlists"`) and the **Add-to-Playlist** picker (`kind == "add-to-playlist"`, multi-select — tick playlists, footer **Add** commits via `Playlists.add-tracks-to-selected`) are thin wiring over it; toolkit components are data-agnostic (`cover`/`subtitle`/`selected`/`disabled` `in` props + a `toggled()` callback). Both commit through the `Dialog.accepted` dispatcher gated on a `*-selected-count > 0`. Add-to-Playlist keeps fully-contained playlists (`contained-count >= pick-total-tracks`) disabled; `set-all-add-picks` + the selection count count only enabled rows. Selection toggles/commit live in `files.rs` (commit needs `Rc<NotificationsUi>`); the picker opener stays in `dialog.rs`. The blur-avoidance rule for `PickerListCard` is a load-bearing Slint pitfall (see `.claude/rules/slint-pitfalls.md`).
- **Reusable notifications stack** (`melodia-ui/ui/components/dialog/notification-stack.slint` + `src/ui/notifications.rs`). Reads `Notifications.rows`; mirrors `Dialog` `kind`-routing — new action = one `if (kind == "…")` branch + one `notifications.show(...)` call. Cap 5. Gotchas: per-card props use `data:` not `row:` (Slint reserves `row` as iter var); translated strings reach Rust via `pure callback`s on `Settings` wrapping `@tr(...)` literals.
- **Backend-thread toasts via `services::toast`.** `NotificationsUi` is `Rc` (UI-thread-only), so backend failures on tokio workers surface through a neutral `OnceLock<UnboundedSender<ToastRequest>>` + `notify(ToastKind, detail)` (no-op when uninstalled; holds no `ui::*` types, preserving the `tasks`-no-`ui` rule). UI-thread consumer `boot::ui_setup::install_toast_bridge` drains the `mpsc` (not a `watch` — errors must not coalesce) into `NotificationsUi::show`, resolving the localized **title** by `ToastKind` (`PlaybackFailed`/`OperationFailed` → `Settings.toast-*-title` `@tr` callbacks); the dynamic **detail** (path / error) is the untranslated body. Producers: `execute_actions` decode-failure (`PlaybackFailed`; the vanished-file skip stays silent), plus the `spawn_logged_toast!` callback macro (log **and** toast) on user-initiated scan/import failures. Routine failures (favorite/rating/nav) keep `spawn_logged!` — don't toast-spam.
- **Anything painting on a hero blur reads `HeroBackdrop`, never a `Theme.*` brush.** The six hero-bearing views (four detail + Favorites + Recently Played) share **one** global, because only one hero can be mounted at a time — each sits under a mutually exclusive `if` in `app-window.slint`, and `ViewTransition` is enter-only, so Slint's `if` destroys the outgoing view instantly. `src/ui/hero_backdrop.rs` (`apply` / `apply_gradient` / `reset`) publishes it from the same `src/ui/backdrop.rs` solve the Now Playing `np-*` tier runs: measure the decoded blur with `luma_p90`, then solve a scrim opacity that drives the *composite* into a known dark band. **The two differ on the seed**: `np-*` takes the hue quantized out of the cover (`ArtworkPair.accent_argb`) and falls back to `Theme.accent`; `apply` seeds from `Theme.accent` unconditionally, since the only tier that surfaces the hue here is `chrome` and every one of its readers is a *missing*-artwork surface with no cover to take a hue from. `apply_gradient` is the exception at both ends — Genre Detail seeds from its own name-hashed `start_rgb` so the chrome tier stays recognisably that genre's. Use `on-backdrop` for the title and the secondary line, `on-backdrop-muted` for the meta/stats line, `chrome` for a placeholder fill or glyph (the `DetailHeader` artwork-tile fallback, the smart-playlist badge, both mosaic heroes' empty state and their `CoverMosaic` placeholder slots). **The hero diverges from `np-*` on the two text tiers: they are fixed `out` constants, not solved.** Pinning the backdrop is what earns that — once every cover lands in the same dark band there is nothing left for a per-artwork text tone to fix, only an album tint to add and a lightness to drift between covers, so fixed reads as one typographic voice instead. Both clear their WCAG targets against the pinned band with margin. `out` is the enforcement: Slint emits no setter, so Rust cannot start writing them again. Only `scrim` / `floor-*` / `chrome` are `in-out`. The rule exists because the pre-solve hero used `Theme.crust.with-alpha(0.45)` as its "scrim" and `Theme.accent.mix(Theme.base, 0.2)` as its floor — both near-white on a light theme, so the same cover painted a dark banner under Mocha and a bright one under Latte and no single foreground colour was right for both. Genre Detail is the one caller keeping its own floor (`apply_gradient`): its stops are name-hashed and already theme-independent, so they are measured rather than replaced. `ActionPill` / `SearchBar` inside a hero are the deliberate exception, and stay on a `Theme.*` brush — each paints `Theme.floating-chrome-bg` (`surface0` at .75, the same token the hero's own back button takes), which is still mostly its own surface, so its contents contrast against `surface0` and not against the blur. That last quarter is only safe because the backdrop is *pinned*: a solved scrim holds the composite in a known tone band, so what bleeds through can't swing between themes. A `chrome`-tinted placeholder is the opposite case — translucent enough that whatever fills the rectangle *behind* it is most of what its glyph composites against, so that fill has to be a hero token too. The two mosaic heroes' artwork square is `HeroBackdrop.floor-start` for exactly that reason — it was `Theme.surface1`, which is near-white under Latte, and dropped a slot's chrome glyph to ~1.2:1 while reading fine under Mocha. **Its 1 px edge had to follow the fill**, and is the case that shows why leaving one theme brush behind is worse than having none solved: a `Theme.border` hairline was a wash against `surface1` under either theme, but against a fill pinned dark it vanishes under Mocha and turns a hard bright ring under every light theme, so it takes `tile-edge` — a derived `out` tier off `on-backdrop`, following the `np-accent-*` precedent below rather than spelling the same alpha in both views. Those two are also the only bordered hero tiles — `DetailHeader`'s is borderless. A hero teardown must `reset`, else the previous entity's colours paint under the next hero until its decode lands. For the three artwork-bearing details it rides in `release_detail_hero_images!`; **Genre Detail and the two mosaic heroes have to call it themselves** — Genre has no images to release so the macro never reaches it, and Favorites / Recently Played reset from their section-leave and empty-mosaic paths.
- **Now-Playing accent tiers are derived on the `Player` global, not at the call site.** One solved brush (`np-accent-bright`) plus three named translucent tiers off it — `np-accent-pill` (.16), `np-accent-disc-hover` (.30), `np-accent-dim` (.60) — following `melodia-ui/ui/theme.slint`'s `floating-chrome-bg` precedent. Reach for the tier, never a fresh `.with-alpha(…)`: the same alphas were spelled out across six files, so two surfaces meant to match could drift with nothing failing. `np-accent-pill` is the resting weight for **every** tinted surface in the view — the metadata chips and the two `AccentDiscButton`s (back, view menu) alike — so the top bar sits at the same tint as the chips under it. Only alphas used **twice or more** earn a name; a genuine one-off (the Up-Next divider, its scrollbar's hover) stays inline, since naming it would move the number without sharing it. `np-accent-disc-hover` is the deliberate exception — a single reader, but that reader is `AccentDiscButton`, which is *itself* the shared surface, so it is named alongside the others and reads as one ladder of weights rather than as a rule and an exception.

## Covers

- **Lazy row covers via the `RowCovers` global.** `TrackListRow` carries no `image` field; `TrackListRowItem` resolves its thumbnail per *instantiated* row through `RowCovers.request(artwork_path)`, wired once in `boot/ui_setup.rs` to the shared row-tier `CoverThumbs`. New TrackList consumers need zero cover plumbing. `CoverThumbs::prewarm` dedupes input and caps work at LRU capacity — pass paths in **display order** so the kept prefix paints first.
- **Cover-prewarm path dedup via `ui::grid_prewarm::unique_artwork_paths`.** One shared `pub fn` turns an iterator of `Option<&str>` artwork paths into a first-seen-ordered, deduped, non-empty `Vec<PathBuf>` for `CoverThumbs::prewarm`. Every entity grid's `first_screenful_paths` (and the genre/album/artist/playlist detail prewarms) calls it — the per-entity wrapper owns only the projection. Don't re-roll the dedup loop; reuse the helper.
- **Albums sub-section borrows `AlbumsUi.grid_covers`.** Artist Detail's Albums strip routes `request-album-cover` to `albums_ui.grid_cover(path)`. `wire_artists` releases on **both** Artists section-leave and `on_close_detail`.

## Releasing what the UI pins

- **Detail-close releases global Image properties.** `wire_{artists,albums}::on_close_detail`: `release_detail_hero_images!` resets `cover` + `blur-img-a/b` to `Image::default()`, clears `has-blur`, alongside `clear_detail` + `release_detail_artwork`. Without it, `SharedPixelBuffer` Arcs pin (~650 KiB CPU + ~1.5 MiB GPU on Mesa). **Sidebar nav-away does NOT trigger** — back button only.
- **Dialog-close releases global Image properties + scalar state — via exactly one handler.** `Dialog.closed()` fires once close-anim `t` returns to ~0, and there is **one** `on_closed` registration in the tree (`callbacks/playlists/dialog.rs`). It does both halves: `Dialog.invoke_closed_teardown()` (the Slint side — `kind`/`target-id`/`input-text*`/`mosaic-*`/`pending-track-ids`/the two picker row models/`title`/`message`/`cancel-label`/`destructive`; restore `confirm-label` to `"OK"`, don't clear to `""`), then `current_artwork` **and** `TagEditor.cover` reset to `Image::default()` (the two `image`-typed global properties, which have no Slint default literal) + `heap_trim::trim`. **The teardown is a Slint `public function`, not a callback body, and that is load-bearing:** a callback has a single handler slot, so a default `closed => { … }` body in `globals/dialog.slint` is installed at `InnerDialog::new()` and then silently **replaced** by the Rust `on_closed` (a plain `Callback::set_handler`). A `public function` has no slot to clobber. `CompositeScroll.reset()` (`globals/shell.slint`) is the second global to take this shape, for the same reason. Do **not** clear in `accepted`/`cancelled` — unmounts body mid-fade. Do **not** re-register `closed` from inside the handler (`Callback::call` `take()`s the handler and asserts). New dialog kind pinning an image extends the single `on_closed` — never adds a second.

## Popups, native dialogs, input

- **PopupWindow auto-dismiss on OS focus loss.** `melodia-ui/ui/components/focus-loss-watcher.slint::FocusLossWatcher` — one-shot component firing `close()` when local `Theme.window-focused` mirror transitions false. Mounted inside `if popup-is-open` so only the open popup has a live watcher; singletons gate on `PopupHighlight.id == "<discriminator>"`; per-row context menu gates on `PopupHighlight.row-ctx-id == row-data.id` (set on right-click, cleared in `winit_filter.rs` Release path). Slint 1.16 has no `closed` callback, but `pop.close()` is a safe no-op when hidden. `changed` MUST watch local mirror — Slint rejects path expressions on globals.
- **Native dialogs (rfd) — always parent to main window.** UI thread via `slint::spawn_local(Compat::new(...))`. Call `.set_parent(&ui.window().window_handle())` before `pick_*()`, else dialog z-orders behind on Win/macOS. Requires `slint = { features = ["raw-window-handle-06"] }`.
- **Keyboard shortcuts** — the root `FocusScope` is `ShortcutScope` (`melodia-ui/ui/layout/shortcut-scope.slint`), which owns every binding below plus the volume-commit debounce; it takes the whole main layout as its children. Grabs focus on `init`, and re-grabs via `shortcut-scope.grab-focus()` on every content-view switch — Slint doesn't hand focus back to an ancestor scope when the focused item is destroyed, so a view unmounting with focus inside it (a filter `SearchBar`) leaves shortcuts dead until the next click. Nine of the root's `changed` mirrors regrab it. Eight are one per branch selector of an `if` chain that mounts a view: `Nav.selected-index`, `Nav.now-playing-open`, the four `*Detail.*-id`s and `mini-switch.render-active` for the content panel, plus `Dialog.kind` for the overlay's own chain (whose bodies die the same way — `closed-teardown()` clears `kind`). Same reason `CompositeScroll.reset()` needs its four, so a new always-mounted mirror that unmounts a *composite* view owes both. The ninth, `Queue.open`, is the exception that isn't about destruction at all: the sheet is permanent and mounts nothing, but its keys sit here and *nothing else moves focus onto it* — the bar button and the overflow entry are TouchArea clicks — so without the grab a filter `SearchBar` keeps the keyboard behind the sheet's backdrop and eats the `a`. Gates non-Esc on `!Dialog.open`. Typed keys in TextInputs never reach root. Bindings: Space play/pause; ←/→ seek ∓5s (Shift ∓30s, Ctrl prev/next); ↑/↓ vol ±5 (Ctrl ±1); 0–9 seek 0–90%; M mute; L favorite; N/P next/prev; S shuffle; R repeat; Q queue sheet (all three queue bindings mini-gated — the sheet doesn't exist in miniplayer mode, and arming `Queue.open` with no mounted mirror to fire `open-changed` remounts it rows-less); F Now Playing; F11 maximize; Esc Dialog cancel → queue sheet (clear selection, then close) → NP close; Ctrl+A queue select-all; Ctrl+B sidebar; Ctrl+, settings; Ctrl+N new playlist; OS media keys via souvlaki. **`ShortcutScope` is the only `FocusScope` in the tree, and the queue sheet is why that's worth stating.** Its Esc / Ctrl+A used to live in a nested `FocusScope { enabled: Queue.open }` inside `queue-sheet.slint`, but a `FocusScope` takes focus on **mouse press** (`i-slint-core/items/input_items.rs`), never on mount — so both keys were dead on a sheet opened with `Q` and only worked after a click on the sheet's blank area, and once the `Dialog.kind` mirror above started regrabbing they died again after any confirm dialog raised from the sheet. Both now sit at the root gated on the scope's `queue-sheet-up` (`Queue.open && !MiniPlayer.active` — the flag alone survives the miniplayer swap that unmounts the sheet), which also fixes the priority: Esc reaches the *dialog* first instead of the sheet's scope, and the `!Dialog.open` gate keeps Ctrl+A from firing behind a modal. A second scope would reintroduce all three problems — put new key handling here.
- **Animated view transitions** — Main-content branches mount via `ViewTransition`: enter-only fade + 32 px axis slide over `Theme.dur-spatial`. No exit anim — Slint `if` destroys outgoing instantly. Direction on `Nav.pending-enter-from: NavEnterFrom` (`{ below, right, left }`) — sidebar=`below`, drill-in=`right`, back=`left`. Write **synchronously on UI thread just before** flipping `if`; routed via `src/ui/nav_transition.rs`. `ViewTransition` flips `shown` via single-shot 1 ms Timer. Panel `clip: true` masks overshoot.

## Settings and nav wiring

- **Section-visibility hooks go through `SectionActiveGate`** (`melodia-ui/ui/components/section-active-gate.slint`), mounted once per sidebar section in `app-window.slint` in nav-index order. It owns the predicate — the section's index is selected *and* neither the full-screen Now Playing view nor the miniplayer is covering it — and fires `active-changed(bool)` into that section's Rust hook, which releases the section's cover caches on the way out and re-warms (or un-dirties) them on the way back in. Non-visual, `FilterThrottle`-style, so it costs no layout. **The gate has to be mounted on the always-alive `AppWindow` root, not inside the view**: the leaving transition is the edge that matters and a view cannot observe its own, since Slint destroys it instantly with no unmount callback. A new section adds one mount, not a tenth copy of the predicate; pass `mini-active: mini-switch.active` (the switch's live derivation, which leads the `MiniPlayer` global by a beat).
- **Nav state persistence keyed by view-id.** All in `views.json` (`ViewStateData`): `last_nav_index` mirrors `Nav.selected-index`; `last_detail_ids: HashMap<String, i64>` holds open detail per tab keyed by `view_id`. Setter `library::settings::set_last_detail_id` writes via `mutate_view_state`. Sidebar nav does NOT reset detail ids; only back button does. Adding detail = `view_id::*` const + open/close `set_last_detail_id` + seed fn. Three section-collapse bools top-level on `ViewStateData`, at clippy's `struct_excessive_bools` cap — **a new persisted view flag has to be an int/string/map, not a fourth bool**; `settings_tab: i32` (the Settings page's active tab) is the worked example, and it sidesteps the cap by being an index rather than five booleans.
- **Settings-page tab bar via `SettingsTabBar`** (`melodia-ui/ui/components/settings/settings-tab-bar.slint`). Data-agnostic — parallel `labels`/`icons` arrays, `avail-width`, `selected-index`, `selected(int)`, the same shape as `ChipGroup`/`Dropdown`/`ColorDotGrid`. **Material 3 tabs: a sliding underline, and no fill on the selected tab** — accent label, accent icon at `filled: true`, and a 3 px `Theme.accent` pill sitting in a gap in the 1 px divider carry it three ways. Hover keeps a state layer (`Theme.surface0`, a rung off `Theme.base` now that the `surface0` track is gone) at `radius-md` rather than the square full-bleed rectangle M3 specifies, matching the settings rows below it. The cell fills its own bounds and the **row** gives the clearance — one `padding-bottom: pad-sm` on the tab `HorizontalLayout` reserves the divider/pill band, so a rounded fill floats above the line instead of resting on it, and the content re-centres in what's left rather than the bar getting taller. That's still the deliberate split from the ChipGroups *inside* the settings rows, which do fill: the bar navigates, the chips configure, and one page showing both needs them to read as different things. **The label weight is constant 500 across both states**, which is load-bearing rather than cosmetic — see the equal-width cells below. **The bar sits in the page header where the "Settings" title used to, flush left, sharing that row with the search bar** — so the divider and underline span the bar rather than the page. The title was deleted rather than displaced: no other page's heading sat directly over five tabs reading Library / Playback / Interface / Services / About, which name the page better than the word above them did, and the sidebar item and window title still carry it. Reclaiming the row is what puts the bar at the top of the page instead of pushing the body down.
  - **The cells are equal width, sized to the widest tab, and that is what makes the underline arithmetic** (`ind-x: tab-w * anim-index`). A `for` loop exposes no per-tab element to read a position off, so a content-sized row would have to snapshot each tab's geometry on selection and go stale on every resize. It costs a little width (5 × widest > sum of naturals) and buys a sliding indicator with no bookkeeping. It is also why the selected label can't be heavier: the cell was measured against one weight.
  - **What eases is two sources; every geometry derives from them unanimated.** `anim-index: root.selected-index` (`dur-med`, `ease-in-out`) owns *a tab was picked*; `compact-t: root.compact ? 1.0 : 0.0` (350 ms, `cubic-bezier(0.2, 0, 0, 1)` — M3 emphasized-decelerate) owns *the bar changed shape*. That duration is inlined rather than taking `dur-spatial`: the flip fires under the user's hand on a resize drag, where a 400 ms tail reads as the bar lagging the window instead of as a gesture. Those two `animate` blocks are the only ones in the file outside the per-cell hover fill and icon colour. **`compact-t` is seeded by that binding and owned by `changed compact`, which writes it** — the binding is live only until the first flip. That is load-bearing at both ends: writing it swaps the animated binding for an animation of its own (`set_animated_value` → `set_binding`), which is what stops a resize drag restarting the curve on every event, and keeping the binding as the seed is what leaves mount alone, since it is still live for the first evaluation and that one lands in `NotAnimating` and takes the value straight through. A constant seed plus a mount `Timer` would morph on every entry into Settings at a compact width. The latch below earns its keep twice over as a result — each `changed compact` is now a real restart, so a threshold that flapped would be visible rather than merely wasteful. **The ease is gated on an `eased` flag a 100 ms mount `Timer` arms**, because the *first* resolution isn't a change — it's the bar learning how much room it has. Since the host seeds its width at the row's floor (below), every mount settles compact and a roomy panel corrects to expanded a frame later; easing that would play an unasked-for morph on every entry into Settings, so it snaps at `0ms` instead. 100 ms rather than the tree's usual 1 ms mount seed is the point — this has to *outlast* the host's first `changed width`, not race it, and no hand crosses the threshold that fast. It resets for free, since the page is rebuilt on every entry. `tab-w` interpolates `natural-tab-w → compact-tab-w` off the second, and `ind-x`, the pill, both divider segments, the bar's own `preferred-width` and the tooltip rect the host builds all fall out of the pair with no `animate` of their own. **They have to be two.** A single `animate` on `ind-x` or the pill's `width` conflates the two events, because both read `tab-w`, and the compact flip then reads as the pill flying in from the right on the way down and from the left on the way back up — its two edges travel different distances. That artifact is the pill *chasing an instant resize*: cell `i`'s left edge is `i * tab-w` and the pill's is `anim-index * tab-w`, so once `tab-w` itself eases, the pill sits under its tab in every frame of the morph rather than only at the ends. (This is why the file used to leave the resize instant and only ease the index — correct about the fix it rejected, wrong about the conclusion.) The divider is two segments cut either side of the pill (`width: ind-x` / `x: ind-x + tab-w`) rather than a line running under it, and they read `ind-x` directly for the same reason — a segment animated on its own would lag the pill by a frame.
  - **The bar sizes itself with `min-width`/`preferred-width`/`max-width`, never a bound `width` — an eased width on a component root moves the whole window's minimum.** Slint reports a root's bound `width` as *both* `min` and `max` (and rejects a `min-width` beside it outright), so binding `width: labels.length * tab-w` puts the bar's layout floor on the animated `tab-w`. That floor climbs the header row into the page and out to the window itself, so the window's own minimum width eases along with the morph: dragging the edge inward chases a wall that is still moving, and it **stutters**. Worse, the bar was then routinely the constraint stopping the window from reaching the very width its own threshold was waiting for, so whether the flip tripped at all came down to whether the title and search row happened to be wider — which is a locale-dependent coin flip, and reads as the responsive switch firing late or not at all. Splitting the three constraints fixes both: `min` is the constant `labels.length * compact-tab-w`, `preferred` tracks the animated cells so a centring host draws it exactly as the bound width did, and `max` keeps the upper half of what that meant. **Any component root whose `width` becomes animated owes this same split** — check `layout_info`'s Horizontal arm in the generated `app-window.rs` if unsure; `min` reading back the root's `width` property is the tell.
  - **Sharing the header row means the two widths are budgeted, not independent.** `avail-width` is no longer the whole page: it's `header-w` (page less its padding) less the two 12 px gaps less whatever the input is taking, so the tabs give up their labels far earlier than they did centred on their own row. Going the other way, `SearchBar`'s slot is fixed-width by design (`input-width`, so focus-scaling never shifts its neighbours), which makes it the page's job to size it — it's driven from `clamp(header-w - bar.compact-w - 2 * pad-md, 140px, 220px)`. **The filter yields before the tabs do**: tabs are navigation, search only refines what a tab already shows. Reserving against the bar's published `compact-w` rather than a restated `5 × 48px` is what keeps the two from drifting, and it makes the row's minimum a sum the page can actually check — see the budget spelled out at `search-w-min`, which is sized against the narrowest panel Settings can be asked to draw in (the 550 px miniplayer cutover, less the sidebar's own floor).
  - **The threshold is latched, not bare.** A slow resize drag delivers a stream of one-pixel widths and a hand jitters over the last of them, so `avail-width < expand-w` flips on every one that straddles the line. Instant, that was invisible; eased, the bar hunts. `compact` compares against `expand-w + (latched ? hysteresis : 0px)` with a 24 px band, and `changed compact => { latched = compact; }` is the only state — the threshold itself is re-derived from `expand-w` every evaluation, so a locale switch still moves it. It converges in one step in both directions and needs no seed `Timer`: `latched` starts `false`, which is the honest reading at mount, and the first real transition corrects it.
  - **The label collapses onto its icon rather than unmounting.** `SettingsTab` takes `compact-t` as a float, not `compact` as a bool, and derives `open: 1.0 - compact-t`: the row's padding and spacing scale with `open`, so the `alignment: center` layout closes to just the icon and the icon glides to the cell's centre with no positioning arithmetic. The label lives in an always-mounted slot whose `width: label-w * open` — an `if !compact:` is what made the flip a pop. Three details are load-bearing: the slot's `clip` is **rectangular and borderless** (a scissor; a rounded one would render the text to an offscreen layer and upscale it on HiDPI), the label's fade is `label-color.with-alpha(…)` rather than `opacity` on the element (`opacity` costs a layer, and there are five cells), and the alpha is a *bias* off the same source — `clamp(1 - compact-t * 2, 0, 1)`, gone by the time the slot is half closed, so the clip never shows a half-eaten word. A second `animate` on the alpha would phase-lag it. `label-w` is `lbl.preferred-width`, read straight off the Text the cell draws: the generated binding is `layout_info(lbl, Horizontal, -1, …).preferred`, which never reads back the width it's handed, so the slot sizing itself from it is a derivation and not a cycle — the same thing that makes the ruler below safe. `cubic-bezier(0.2, 0, 0, 1)` keeps both y control points inside `[0, 1]`, so `compact-t` can't overshoot and no derived width goes negative; a back-out curve would need `clamp` on `open`.
  - **`compact` is measured, not thresholded.** A hidden `measure := VerticalLayout { visible: false; … }` mounts one **real** `SettingsTab` per label — the same component the bar draws, so the measured shape and the drawn shape cannot drift — and `measure.preferred-width` is the widest expanded cell. `compact: avail-width < labels.length * that`. The labels are translated, so the width that matters is the running locale's; the predecessor was a hand-derived `page-w < 780px` literal whose own comment ended "re-check it when adding a locale", and that obligation is now gone. **`compact` stays an instant bool on purpose** — it is the *decision*, and `compact-t` is that decision rendered over time. That split alone does **not** make easing the flip safe while `avail-width` changes continuously under a resize drag, and the claim that it did was wrong for a subtle reason worth keeping: Slint restarts an animated *binding* on dependency **dirtiness**, never comparing values, so it is irrelevant that the bool only ever sees a toggle — `compact` reads `avail-width`, the drag rewrites it on every pointer motion, and the 350 ms curve was torn down and restarted every few milliseconds. The gate is that `compact-t` is **written** from `changed compact` rather than left to its binding; see the sources bullet above and the pitfalls entry. The *threshold* can't chase the flip either — the ruler is always expanded (the drawn cells pass `compact-t`, the ruler's pass `0.0`), so `natural-tab-w` doesn't move when `compact` flips, nor while the flip is playing out. That is a different guarantee from not flapping under a jittering drag, which is the latch's job — see below. **The decision had to move into the bar**: a component may read `preferred-width` off its own descendant but not off a child component's internals (`menu-surface.slint`, `overflow-menu.slint` state the rule), so the host can only hand over `avail-width` and read the verdict back. It still hands over a **mirrored** width (`changed width => { self.page-w = self.width; }`, the `now-playing-bar.slint` `bar-w` idiom) — a live `root.width` read feeding a child's size re-enters layout — and it's the **content panel** less its own padding, not the window. **The mirror costs a frame, so what `page-w` is seeded to is a real decision, and it has to be the header row's own floor rather than a plausible page width.** The failure is asymmetric: seeded wide, the bar believes it can afford five full-width tabs and draws them into a panel that can't seat them, and under `alignment: start` with no clip at that level they spill out from under the row and under the search bar. Seeded at the floor it draws the icons it would have drawn anyway and widens once. A **miniplayer → full swap remounts the page at a panel far narrower than any plausible guess**, which is the reliable way to see the wide one — a literal `900px` sat there and looked harmless until exactly that. The floor is spelled `2 * pad-lg + bar.compact-w + 2 * pad-md + search-w-max`, the narrowest page that still seats the bar at `compact-w` *and* the input at `search-w-max`, so at the widths Settings is normally opened at neither pops a frame later; `ui::settings_page::tests::the_page_width_seed_is_the_rows_floor` pins that it stays derived. **A seed obliges a mount `Timer`**: `changed` doesn't fire when the first layout settles directly on the final value, and a window opened at its final size is exactly that — so without the 1 ms single-shot beside it the seed is never corrected and a roomy window still draws icon-only tabs until something resizes it. It only looked right coming out of the miniplayer, where the floor's answer happens to be the correct one.
  - `visible: false` is the right hiding mechanism here and worth knowing why: it lowers (`i-slint-compiler/passes/visible.rs`) to an injected `Clip` parent with `clip: !visible`, and that pass runs **after** `default_geometry`, so the injected element gets no geometry bindings and sits at 0×0. Nothing paints, `Clip::input_event_filter_before_children` intercepts anything outside its empty rect so the five hidden `TouchArea`s are unreachable, and the layout info the ruler exists for is still computed — the "`visible: false` doesn't remove from layout" pitfall read the useful way round. The generated `measure_…_layoutinfo_h` is a `box_layout_info_ortho` over the repeater with a `None` cross-axis constraint, i.e. it never reads the assigned width, which is what keeps `measure.width ← bar.width ← measure.preferred-width` from being a cycle.
  - **The compact tooltip is not on the tab**: the bar publishes `hovered-idx` (-1 for none) and `hovered-label`, fed by a per-tab `hover-changed(bool)` off a local `has-hover` mirror, and `settings-view.slint` hangs one `Tooltip { side: TooltipSide.below }` off a frame declared **after** both `OverlayScrollbar`s. Anchored on the tab it would sit inside the page header, which Slint paints *before* the scroll body, so the first section card covers it — the same fix, and the same frame-tracks-the-host idiom, as `playlists-view.slint`'s `header-tip`. Equal-width cells let the host derive the rect from the index (`bar.absolute-position.x - root.absolute-position.x + bar.tab-w * bar.hovered-idx`), so unlike the snapshot this replaced, a tab that moves under a parked pointer (Ctrl+B, F11) keeps its tooltip anchored to it — and since `tab-w` eases, that frame morphs with the cell for free. The gate stays on the instant `compact` rather than on `compact-t`: `Tooltip` owns a 500 ms reveal delay, longer than the 400 ms morph, so it can't surface while the label is still readable. Only the tab that owns the hover may retract it — keyed on its **index**, since a data-agnostic bar can be handed two tabs with one label — else a leave arriving after the neighbour's enter blanks a live one. Tab switches reset `sv.viewport-y` imperatively from two local `changed` mirrors — a short tab under a parked offset otherwise paints blank.
- **Audio installers seed from `ui::settings_bind::read_or_default(state, "…")`.** `install_{equalizer,replaygain,visualizer}` each opened with the same `match settings::read_settings(…)`, spelling its own defaults out again in the error arm — a second copy of the `Default` impl, and a second place for it to drift. The helper falls back to `SettingsData::default()` and logs, so the seed is derived one way whether the file loaded or not. Its sibling `toggle_binding` still owns the apply-then-persist shape. **Not every installer wants it:** `playback_settings` / `file_watching` / `updater_settings` use `if let Ok(s)` deliberately, leaving the **Slint-declared** defaults in place on a read failure rather than re-deriving them in Rust — converting those would change their fallback, not de-duplicate it.
